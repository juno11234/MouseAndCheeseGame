# 데이터 테이블 (Google 스프레드시트 → ScriptableObject 에디터 임포트 파이프라인) 기능 매뉴얼

- 작성 날짜: 2026-09-24 (26_0924)
- 작성자: builder (Claude Code)
- 참고 계획 파일: `Assets/Ignore/Task/Plan/26_0924_데이터테이블_plan.md` (2절 신규 파일 목록, 4-2~4-4절 코드 스니펫, 4-6절 "다음 단계" 3번 항목까지 그대로 구현)
- 구현 범위: 코드 5개 파일(신규 5, 수정 0). 계획서 4-6절 "다음 단계"의 1·2·4·5번(시트 공유 설정 변경, 시트에 실제 값 채우기, Play 모드 검증, 0-5/0-8 확인)은 사용자 지시로 이번 세션 범위 밖이라 수행하지 않았다.

## 1. 기능 요약

Google 스프레드시트("MouseAndCheeseTable")에서 5개 게임 밸런싱 ScriptableObject 에셋(`PlayerStatData`, `CatStatData`, `LeafFlightData`, `ObjectSpawnData`, `ScoreData`)의 필드 값을 에디터 메뉴 한 번으로 가져와 채우는 파이프라인이다.

- **데이터 흐름**: `DataTableFetcher.FetchGrid()`(공개 TSV export, 인증 불필요) → `DataTableRowParser.Parse()`(원시 셀 격자 → `List<DataTableRow>`) → `DataTableAssetWriter.Apply()`(`SerializedProperty`로 값 대입, `tableName`이 일치하는 행만) 세 단계를, `DataTableImportMenu.Import()`가 5개 에셋에 대해 묶어서 실행하는 에디터 메뉴 진입점(`MouseAndCheese/Data Table/Import From Sheet`)이다.
- **대상에서 제외된 것**: `SpeedEffectData`(계획 0-1절 결정, 이번 데이터 테이블 대상이 아님), `PlayerStatData._hungerToSpeedCurve`(`AnimationCurve` 필드, 계획 0-6절 결정, 계속 Inspector에서 수동 관리).
- **에디터 전용**: 축 1(에디터 시점)·축 2(공개 TSV export, 인증 불필요)가 모두 결정되어(계획 0-3절), 빌드에는 아무 자격 증명도 포함되지 않는다. `UnityEditor`를 참조하는 3개 파일(`DataTableFetcher`, `DataTableAssetWriter`, `DataTableImportMenu`)은 전부 `Editor` 폴더 아래 있어 플레이어 빌드에서 자동 제외된다.
- **기존 코드 미변경**: 6개 SO 클래스(`SpeedEffectData` 포함)와 그 소비 코드(`HungerController`, `CatController`, `Player`, `LeafFlightTrigger`, `ObjectSpawner`, `SpeedEffectController`, `ScoreController` 등)는 전혀 수정하지 않았다(계획 3절 "없음" 원칙, 0-4절 근거).
- **이번 세션에서 하지 않은 것**(사용자 지시로 범위 밖): 실제 스프레드시트에 컬럼·값 입력, 시트 공유 설정("링크가 있는 모든 사용자") 변경.

## 2. 신규 파일 목록

| 파일 경로 | 내용 |
|---|---|
| `Assets/02_Scripts/DataTable/DataTableRow.cs` | 시트 한 행(`TableName`/`FieldName`/`ValueType`/`Value`/`Description`)을 담는 순수 데이터 클래스. `UnityEditor` 미참조라 `Editor` 폴더 밖에 위치(런타임 어셈블리에도 포함, 계획 2-1절 근거) |
| `Assets/02_Scripts/DataTable/DataTableRowParser.cs` | 원시 셀 격자(`IReadOnlyList<string[]>`)를 `List<DataTableRow>`로 변환. 첫 행(헤더)은 건너뛰고, `Table/Field/Type/Value/Description` 5개 컬럼을 인덱스 상수로 파싱 |
| `Assets/02_Scripts/DataTable/Editor/DataTableFetcher.cs` | 공개 TSV export URL(`SpreadsheetId` 하드코딩, `SheetGid = 0`)로 `UnityWebRequest`를 동기 대기하며 다운로드한 뒤 탭·줄바꿈 기준으로 셀 격자를 만든다. 다운로드 실패 시 `Debug.LogError`로 원인(시트 공유 설정 확인 안내 포함)을 남기고 빈 격자를 반환 |
| `Assets/02_Scripts/DataTable/Editor/DataTableAssetWriter.cs` | `DataTableRow` 목록 중 `tableName`이 일치하는 행만 골라 `SerializedObject`/`SerializedProperty`로 대상 SO에 값을 적용(`float`/`int`/`bool`). `PascalCase` 프로퍼티 이름을 `_camelCase` 백킹 필드 이름으로 기계적으로 변환(`ToBackingFieldName`). 로케일 문제를 막기 위해 `CultureInfo.InvariantCulture`로 파싱 |
| `Assets/02_Scripts/DataTable/Editor/DataTableImportMenu.cs` | `[MenuItem("MouseAndCheese/Data Table/Import From Sheet")]` 진입점. 5개 SO 에셋 경로·테이블명 쌍(`ImportTarget` 구조체 배열)을 순회하며 `FetchGrid → Parse → Apply`를 연결하고 `AssetDatabase.SaveAssets()` 호출. 계획서 "4-6. 다음 단계" 3번 항목을 구현한 파일로, 계획서 "2. 신규 파일 목록" 표에는 없어 클래스 설계(이름, 메뉴 경로, 순회 방식)를 이번 구현에서 새로 정했다 |

수정한 파일은 없다. `PlayerStatData.cs`, `CatStatData.cs`, `LeafFlightData.cs`, `ObjectSpawnData.cs`, `SpeedEffectData.cs`, `ScoreData.cs` 6개 SO 클래스와 이들을 참조하는 소비 코드 전부(`HungerController`, `CatController`, `Player`, `LeafFlightTrigger`, `ObjectSpawner`, `SpeedEffectController`, `ScoreController` 등)를 손대지 않았다(계획 3절 그대로).

## 3. 사용 방법 (Unity Editor)

1. Unity 메뉴에서 `MouseAndCheese > Data Table > Import From Sheet`를 선택한다.
2. 내부적으로 시트를 동기 다운로드(그동안 에디터가 잠깐 멈춘다) → 파싱 → 5개 에셋(`Assets/05_Data/PlayerStatData.asset`, `CatStatData.asset`, `LeafFlightData.asset`, `ObjectSpawnData.asset`, `ScoreData.asset`)에 순서대로 값 적용 → `AssetDatabase.SaveAssets()` → `Debug.Log`로 "N개 행을 5개 에셋에 적용했습니다" 로그가 남는다.
3. 시트에 없는 필드(`TableName` 불일치이거나 `FindProperty`가 실패하는 필드명)는 조용히 건너뛴다 — 정상 동작이며 오류가 아니다.
4. `AnimationCurve` 필드(`PlayerStatData._hungerToSpeedCurve`)는 시트에 행을 넣어도 무시된다. `DataTableAssetWriter.ApplyValue`의 `switch`가 `Float`/`Integer`/`Boolean`만 처리하기 때문이다(계획 4-5절).

## 4. 전제 조건 (아직 충족되지 않음, 이번 세션 범위 밖)

- "MouseAndCheeseTable" 시트가 "링크가 있는 모든 사용자 - 보기 가능"으로 공유돼 있어야 한다(계획 0-7절). 실제 공유 상태는 이번 세션에서 확인·변경하지 않았다.
- 시트에 계획 4-1절 스키마(`Table`/`Field`/`Type`/`Value`/`Description` 5열, 헤더 1행 + 데이터 행)로 5개 클래스·38개 필드의 실제 값이 채워져 있어야 한다. 이번 세션에서는 채우지 않았다(사용자 지시로 범위 제외).
- `DataTableFetcher.SheetGid = 0`은 "DataTable" 탭이 시트의 첫 번째(기본) 탭이라는 가정이다. 별도 탭으로 새로 만들면 그 탭의 실제 `gid` 값으로 코드를 고쳐야 한다(계획 4-3절 캐비엇 그대로).

이 세 가지가 충족되지 않은 상태에서 지금 메뉴를 실행하면 다운로드가 실패(`Debug.LogError`)하거나, 빈/헤더뿐인 시트를 받아 적용되는 행이 0개인 채로 조용히 끝난다(에셋 값은 바뀌지 않는다).

## 5. 컴파일 검증 상태

- 이번 세션 도중 사용자의 Unity Editor(6000.3.19f1)가 이미 이 프로젝트를 열어둔 상태였고, 파일 생성 중 자동 에셋 리프레시가 걸려 실제 스크립트 컴파일이 수행된 것을 `Editor.log`로 직접 확인했다.
- 그 컴파일 패스(`*** Tundra build success`, 두 어셈블리 모두 `ExitCode: 0`, `error CS` 없음)에는 `DataTableRow.cs`, `DataTableRowParser.cs`, `DataTableFetcher.cs` 3개 파일이 포함되어 성공적으로 컴파일됐다.
- `DataTableAssetWriter.cs`·`DataTableImportMenu.cs`는 그 이후에 작성돼 이번 세션 중 추가 리프레시가 발생하지 않았다. 이미 열려 있는 Unity 인스턴스와 동시에 별도 배치 모드 컴파일을 강제로 실행하면 프로젝트 잠금 충돌 위험이 있어 시도하지 않았다. 두 파일은 코드 리뷰로 문법과 API 시그니처(`SerializedObject`/`SerializedProperty`/`SerializedPropertyType`/`EditorUtility.SetDirty`/`AssetDatabase.LoadAssetAtPath`/`MenuItem` 등)를 대조 확인했지만, 실제 컴파일 성공 여부는 사용자가 Unity Editor로 포커스를 돌려(자동 리프레시 유도) 콘솔에서 최종 확인해야 한다.
- 메뉴 실행 결과(시트 값이 실제로 5개 에셋에 올바르게 반영되는지)와 Play 모드 동작은 4절의 전제 조건이 충족되지 않아 검증하지 못했다.

## 7. 계획서와 달랐던 점

- 계획서 4-2~4-4절 코드 스니펫은 전부 그대로 옮겼다. 다만 `DataTableRow.cs`는 클래스 내부에 컬렉션 타입을 전혀 쓰지 않아 실제로는 불필요했던 `using System.Collections.Generic;` 한 줄만 제거했다(계획서 4-2절 스니펫에는 두 클래스 모두에 이 using이 있었으나, `DataTableRow`에는 `List`/`IReadOnlyList` 사용이 없다). 동작에는 영향이 없다.
- `DataTableImportMenu.cs`(5번째 파일)는 계획서 "2. 신규 파일 목록" 표에는 없고 "4-6. 다음 단계" 3번 항목("...에디터 메뉴 진입점을 추가한다")으로만 서술돼 있어, 구체 설계(클래스명 `DataTableImportMenu`, 메뉴 경로 `MouseAndCheese/Data Table/Import From Sheet`, `ImportTarget` 구조체로 5개 에셋 경로·테이블명을 순회하는 방식)는 이번 구현에서 새로 정했다.
