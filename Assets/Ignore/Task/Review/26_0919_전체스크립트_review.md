## 1. 코드 리뷰

### 🔴 버그 가능성

#### R1. 갭(Gap)이 실제 거리와 어긋남 — 영향도: 높음
- 파일/줄: `CatController.cs` 51, 66, 136-140 / `PlayerPathRecorder.cs` 61-63
- 문제: 갭 = 플레이어 누적 이동거리(P) − 고양이 누적 이동거리(C). 이 값이 "경로상 거리"가 되려면 ① 시작 시 실제 거리 = InitialGap, ② 고양이가 플레이어와 같은 길이를 걷는다는 두 조건이 필요한데, 둘 다 성립하지 않는다. 계산 갭 = 실제 갭 + 오차라고 두면 오차가 세 방향에서 생긴다.
  1. **초기값 출처가 두 곳 (오차를 음수로)**: `InitialGap`(5)과 씬 배치가 따로 논다. 씬의 Cat (-42.98, 0.16, 6.22) ↔ Player (-45.9, 11, 24.8)는 직선만 약 21.7m(높이 차 약 10.8m)이고 NavMesh 경로는 더 길다. 고양이가 첫 경로점까지 걷는 거리가 전부 C에 쌓이므로 갭이 (실제 시작 거리 − 5)만큼 작게 계산된다. 시작 직후 낙하가 있으면 그 거리가 P에 쌓여 반대로 상쇄되는 등, 결과가 배치에 따라 우연히 정해진다.
  2. **수직 이동 누적 (오차를 양수로)**: 두 오도미터가 3D 거리(`Vector3.Distance`)를 쌓는다. 점프·비행 상승·낙하는 P에만 쌓이고 NavMesh 위를 걷는 고양이는 따라 걸을 수 없다. 제자리 2단 점프 1회 최대 약 +3.3m(jumpForce 4 → 정점 약 0.82m), 제자리 비행 1회 약 +30m(3m/s × 5초 상승 + 낙하). 이동 중 비행도 대략 10m 안팎이 더해진다(추정).
  3. **코너 컷팅 (오차를 양수로)**: 경로점 간격(씬 오버라이드 20~40프레임 → 60fps·10m/s 기준 3.3~6.7m), `WaypointArrivalTolerance` 1m 조기 전환, DirectChasing 직선 추격 때문에 고양이 경로는 늘 플레이어 경로보다 짧다.
- 결과: 실제 경로 갭은 음수가 될 수 없으므로 오차 < 0이면 **|오차|만큼 떨어져 있어도 Caught**(Path Replay가 막으려던 불공정 캐치), 오차 > 0이면 고양이가 붙어도 C가 P보다 빨리 늘 수 없어 **영원히 못 잡는다**(제자리 비행 1회 ≈ 무적). 오차는 플레이할수록 양수 쪽으로만 쌓이므로 게임이 "원거리 포획" 구간에서 "포획 불가" 구간으로 흘러간다.
- 수정 방법
  - 단기: (1) 두 오도미터 모두 **수평(XZ) 거리만** 누적(아래 유틸을 두 곳에서 공용 사용). (2) 초기 갭을 실측으로: `Start`에서 `NavMesh.CalculatePath(고양이→플레이어)` 코너 길이 합을 `_catTraveledDistance = -길이`로 사용(또는 고양이를 런타임에 "InitialGap만큼 뒤"에 배치). (3) [기획 확인] 오차가 남는 동안 "붙었는데 안 잡힘"을 막는 접촉 포획(`DistanceToPlayer <= CatchDistance`) 병행 여부 결정.
  - 장기: 갭을 "기록된 경로 위의 남은 길이"로 재정의 (설계 평가 🏗️-1).

```csharp
/// <summary>
/// 두 위치 사이의 수평(XZ) 거리. 고양이가 걸어서 따라갈 수 없는 수직 이동을 갭 계산에서 제외한다
/// </summary>
public static float HorizontalDistance(Vector3 from, Vector3 to)
{
    Vector3 delta = to - from;
    delta.y = 0f;
    return delta.magnitude;
}
```

#### R2. GapCorrecting 종료 조건이 허용 구간을 건너뛸 수 있음 — 영향도: 높음
- 파일/줄: `CatController.cs` 115
- 문제: `Mathf.Abs(Gap - snapshot) <= 0.1` → 구간 폭 0.2m. 프레임당 갭 감소량 ≈ (보정 속도 10 − 플레이어 속도) × deltaTime. 플레이어 2m/s·30fps면 프레임당 0.27m, 60fps도 50ms 히치 한 번이면 0.4m로 구간을 건너뛴다. 건너뛴 뒤에는 구간으로 돌아올 일이 사실상 없어 10m/s 보정이 계속되고, 갭이 0에 닿으면 Caught(오차 상태에 따라서는 붙은 채 영구 보정). GapCorrecting 중에는 DirectChasing·러버밴딩이 꺼지고 타임아웃도 없어, R1의 수직 누적으로 스냅샷에 못 닿으면 이 상태에 갇힌다.
- 수정 방법: 보정 중 갭은 스냅샷 위에서 아래로만 줄어들므로 단방향 비교로 충분하다. 최대 보정 시간 폴백(`CatStatData`에 값 추가)도 권장.

```csharp
// 보정 중 갭은 스냅샷 위에서 아래로만 줄어들므로 단방향 비교로 허용 구간 건너뛰기를 막는다
if (Gap <= _gapSnapshotAtFlightStart + _catStatData.GapCorrectionTolerance)
{
    SetState(CatState.Chasing);
}
```

#### R3. Chasing ↔ DirectChasing 경계 진동과 반복 큐 삭제 — 영향도: 중간
- 파일/줄: `CatController.cs` 99, 107, 147, 180, 190-194
- 문제: 진입(`<= 10m`)과 이탈(`> 10m`) 기준이 같고(히스테리시스 없음), 상태별 속도가 불연속이다(Chasing은 갭 > 15면 8m/s, DirectChasing은 항상 4m/s). 갭 > 15(R1 때문에 흔함)이고 플레이어가 약 6m/s면: 8m/s로 진입 → 4m/s로 감속 → 멀어져 이탈 → `ClearQueue()` → 큐가 비어 에이전트가 직전 목적지(플레이어 위치)로 8m/s 전진 → 재진입… 이 몇 프레임마다 반복된다. 속도가 떨리고, 이탈할 때마다 경로가 지워져 **Path Replay 대신 직선 추격만 남는다**. 에셋 값 `DirectChaseDistance = 10`이 커서 이 구간에 자주 들어간다.
- 수정 방법: 이탈 기준에 여유폭을 둔다(`DirectChaseExitMargin`, 예: 진입 + 2m). DirectChasing도 `ResolveChasingSpeed()`를 써서 속도 정책을 통일한다. 이탈 시 큐 전체 삭제 대신 "고양이보다 뒤쪽 점"만 버리는 방식도 검토한다(요구사항 "상태 변경 이후 경로만 추적"과 합의 필요).

#### R4. 접지 판정이 공중에서도 true — 영향도: 중간 (일부 [검증 필요])
- 파일/줄: `Player.cs` 131-133 (씬 오버라이드 groundCheckRadius 0.5 / groundCheckDistance 0.5)
- 문제 1 (값과 기하로 확정): 원점이 발(`transform.position`, CharacterController center 0.5·height 1의 캡슐 바닥)이고 반지름 0.5 + 거리 0.5라서 발이 바닥 위 **최대 약 1.0m**까지 떠 있어도 접지로 판정된다. 점프 정점(약 0.9m)에서 내려오는 동안 `_jumpCount = 0`, `_velocity.y = -2`가 적용되므로, 착지 전 재점프로 2단 제한이 무력화되고(연속하면 무한 점프) 하강이 2m/s로 꺾여 둥둥 뜬다. 판정 구 반지름(0.5)이 캐릭터 반지름(0.25)의 두 배라 공중에서 옆 가구 모서리에도 걸린다.
- 문제 2 [검증 필요]: Unity 문서에 "SphereCast will not detect colliders for which the sphere overlaps the collider"라고 되어 있다. 서 있을 때 시작 구가 이미 바닥과 겹치므로 바닥이 BoxCollider(씬 콜라이더 34개 중 28개)라면 서 있는 동안 false일 수 있다. 그러면 지상에서 `_velocity.y`가 −9.81까지 쌓여 턱에서 떨어질 때 가속 없이 최고 속도로 낙하한다. 확인법: 평지에 가만히 서서 `IsGrounded()` 반환값을 임시로 출력.
- 수정 방법 (택1): (A) `Move`를 한 번으로 합친 뒤(B3) `_characterController.isGrounded` 사용(표준 방식). (B) 원점을 `transform.position + Vector3.up * (groundCheckRadius + 0.05f)`로 올리고 거리를 `0.05f + groundCheckDistance`로 캐스트. 반지름은 캐릭터 반지름 이하, 거리는 skinWidth(0.08) + 여유 수준으로 다시 조정한다(씬 오버라이드 값도 함께 조정).

#### R5. 음식·함정이 소비되지 않아 재진입마다 반복 적용 — 영향도: 중간, [기획 확인]

- 문제: 적용 후 비활성화/반환 경로가 없다. Cheese_Obj(+100, MaxHunger 50)는 트리거를 나갔다 들어오면 무한 풀 회복, Trap_Obj(−10)는 재진입마다 반복 감소, 먹은 음식도 화면에 남는다.

#### R6. Leaf.prefab의 `_leafFlightData`가 프리팹 레벨에서 비어 있음 (직렬화 연결) — 영향도: 중간

## 2. 설계 평가

### 🏗️ 설계 적합성
- **1) 갭 모델 — ❌ 문제**
  - 근거: 승패 판정이 "각자 걸은 거리의 차"라는 간접 추정치다. "고양이가 플레이어 경로의 어디쯤 있나"라는 같은 사실을 경로 큐와 오도미터 두 곳에서 따로 표현해, 둘이 어긋나면 오차가 쌓이고 스스로 복구되지 않는다(R1).
  - 조언: 경로점에 기록 시점의 플레이어 누적 수평 거리를 함께 저장하면 갭을 경로 자체에서 계산할 수 있다. `PathPoint { Position, Distance }`, 고양이 진행도 = 목표점.Distance − `agent.remainingDistance`, Gap = 플레이어 누적 거리 − 고양이 진행도. 고양이가 지름길로 가든 링크를 타든 "플레이어 경로 위 위치"로 재므로 오차가 쌓이지 않는다. 시작 거리는 자동 반영되고(InitialGap 이중 출처 해소), 비행 중엔 수평 비행 거리만큼만 벌어져 스냅샷 복원 = 물리적 복원이 된다(요구사항 "비행은 갭에 중립"과 일치). 비용은 지금과 같은 O(1)이다. 파괴적 `Queue` 대신 리스트 + 고양이별 커서로 바꾸면 다중 고양이 확장도 열린다.
- **2) 추상화 수준 — ⚠️ 주의**
  - 근거: `IHungerObj`는 필요한 만큼만 추상화했다 ✅. 반면 고양이는 Player 내부 enum을 직접 해석한다(Fly면 정지, 아니면 보정). 고양이가 알아야 할 것은 "날고 있나"가 아니라 "지상 경로가 끊겼나 / 갭 중립 구간인가"다.
  - 조언: Player가 의미 단위 신호(접지 여부, 실제 착지 시점)를 내면 새 이동 상태가 생겨도 고양이·레코더를 고칠 필요가 없다. 지금 규모라면 `MoveState`, `IsGrounded` 공개와 착지 이벤트 정도면 충분하다. 이렇게 하면 갭 보정 시작 시점도 공중(Fly→Run)이 아니라 실제 착지가 된다.
- **3) 패턴 선택 — ⚠️ 주의**
  - 근거: Path Replay + NavMeshAgent는 "지름길 추격 방지"라는 목표에 맞는 선택이다 ✅. 다만 직선거리 10m 직접 추격이 높이 차와 벽을 무시하고 최단 경로로 직행해 그 전제와 부딪히고, 상태 전이 규칙(히스테리시스·가드·타임아웃)이 없다(R2·R3·R7).
  - 조언: 직접 추격 판정에 수평 거리 + 높이 차 제한(또는 `NavMesh.Raycast` 가시성)을 더하고, `SetState`에 허용 전이 표를 두어 이상 전이를 한 곳에서 잡는다.

### 📈 확장성
- **1) 새 음식/장애물 — ⚠️ 주의**: 프리팹과 수치만으로 추가되는 데이터 주도 구조다 ✅. 하지만 소비 계약이 없고(R5), Apple_Obj 프리팹은 트리거만 있고 `Food` 컴포넌트가 없어 먹어도 효과가 없다. 스폰 Feature 전에 소비 훅을 넣어 두면 스폰 쪽은 "소비되면 풀 반환"만 구현하면 된다.
- **2) 새 이동 상태 — ❌ 문제**: `PlayerMoveState` 분기가 `Player.Update`(switch), `SetMoveState`(if/else), 레코더(`!= Run`), 고양이(`Fly`/else) 네 곳에 흩어져 있고, 고양이의 else는 새 상태를 착지로 오해한다(R7). 하나라도 빠뜨리면 조용히 오동작하므로, 구독자는 관심 있는 상태만 `switch`로 명시 처리하고 나머지는 무시하게 한다.
- **3) 의존 방향 — ⚠️ 주의**
  - (a) 게임 로직(이동 방향)이 연출(`CameraController.ForwardDirection`)에 의존하고 A/D 입력도 카메라가 읽는다. 카메라 셰이크나 연출 카메라가 들어오면 이동 방향이 흔들린다 → 방향(yaw)은 Player가 소유하고 카메라가 따라가게 뒤집는다. "카메라 = 조향"이 의도된 디자인이라도 입력 → 헤딩 계산만은 카메라 밖으로 뺀다.
  - (b) Player 쪽 레코더가 적의 Transform을 `[SerializeField]`로 참조해 Cat ↔ Player 양방향 의존이 생겼다(Player 프리팹 단독으론 NRE, 고양이 스폰·다중화 차단) → 고양이가 `OnEnable`에서 `_pathRecorder.RegisterChaser(transform)`으로 스스로 등록하게 한다.

### 🔧 유지보수성
- **1) 흐름 추적 — ✅ 양호**: 커스텀 델리게이트 + 대칭 구독이 일관되고, `ChangeHunger`/`SetMoveState`/`SetState`로 상태 변경이 한 곳에 모여 있다. 폴더도 기능 단위로 명확하다.
- **2) 데이터와 책임 경계 — ⚠️ 주의**: 튜닝 값이 네 곳에 흩어져 있다. ① SO 3종, ② 컴포넌트 필드 + 씬 오버라이드(레코더 간격 20/40, 접지 0.5/0.5), ③ 하드코딩(비행 8f, 회전 720, 중력), ④ 효과 없는 씬 값(Cat NavMeshAgent speed 6은 코드가 매 프레임 덮어씀). "튜닝 값은 SO, 씬 오브젝트 참조만 씬"으로 규칙을 정하면 값을 찾는 곳이 하나가 된다. 레코더 간격 값은 성격상 CatStatData 쪽이 맞다.
- **3) 테스트·디버깅 — ❌ 문제**: 갭은 보이지 않는 가상 수치인데 관찰 수단이 매 프레임 로그뿐이라 "왜 저기서 잡혔나 / 왜 안 잡히나"를 추적할 수 없다. 레코더 `OnDrawGizmosSelected`로 경로점·선을, 고양이로 목표점·상태·갭을 씬 뷰에 그린다. 갭 계산과 전이 판정을 순수 C# 클래스(예: `ChaseModel`)로 떼면 EditMode 테스트로 R1~R3 시나리오를 고정할 수 있다.
- **4) 주석·문서 — ⚠️ 주의**: summary 작성률은 높다 ✅. 하지만 옛 설명과 계획서 절 번호가 남아 오해를 부른다(B9). 26_0918 매뉴얼의 `MoveState`/`FlightTimeRatio`/착지 판정은 코드에 없다. 주석에는 "왜"를 한 줄로 풀어 쓰고, 기능을 바꾸면 같은 커밋에서 주석도 고친다.

## 3. 전체 요약

### 심각도별 건수

| 구분 | 건수 |
|---|---|
| 🔴 버그 가능성 | 8 (높음 2 / 중간 4 / 낮음 2) — R1~R8 |

| 🔵 아키텍처/개선 | 14 — B1~B14 |
| 설계 평가(🏗️·📈·🔧 10항목) | ✅ 1 / ⚠️ 6 / ❌ 3 |

### 전반적 평가
코드 위생은 좋다. 컨벤션 준수율이 높고(var 0, 접근 제어자 명시, 구독 해제 누락 0), 시스템마다 크기가 알맞고 과잉 설계가 없다. 배고픔·풀잎 비행·입력·카메라는 규모에 맞게 짜여 있다. 문제는 가장 최근에 들어온 고양이 AI의 **갭 모델**에 몰려 있다. 승패 판정이 실제 공간과 따로 노는 누적 추정치라서, 상태 경계 처리 미비(R2·R3·R7)와 겹치면 "멀리서 잡힘 / 붙어도 안 잡힘 / 갑자기 폭주"가 뚜렷한 재현 조건 없이 나타날 수 있다. 게임오버·스폰 Feature를 올리기 전에 이 토대를 먼저 다지는 것을 권한다.

### 현재 설계의 강점
1. 데이터 주도: SO 스텁으로 밸런싱을 분리했고, `IHungerObj` 값만으로 음식/장애물을 표현한다(치즈 풀 회복을 clamp로 처리한 발상이 깔끔함)
2. 느슨한 훅: Player는 고양이를 모르고 이벤트만 발행해, 고양이 AI를 기존 파일 수정 없이 추가했다
3. 단일 변경 경로(`ChangeHunger`/`SetMoveState`/`SetState`)로 상태 추적이 쉽다
4. 이벤트 위생: 전 파일 대칭 구독, 누락 0건
5. 규모에 맞는 단순함과 일관된 fail-fast

### 가장 시급한 개선 포인트
