## 0. 확정되지 않아 이번 계획에서 임의로 결정하지 않은 사항 (구현 단계 전 확인 필요)

1. **장애물(쥐덫) 섭취 시 감점 여부**: GDD·Task 어디에도 "장애물 페널티가 점수에도 반영된다"는 언급이 없다(배고픔 감소는 이미 `HungerController`가 처리 중). 이 계획은 장애물 섭취를 점수 계산에서 완전히 무시한다(4-2절 `HandleFoodConsumed`). 감점이 필요하면 별도 확인 후 `ScoreData`에 필드를 추가해야 한다.
2. **최고기록 초기화(리셋) 기능 필요 여부**: 명시 없음. 이 계획은 저장/불러오기만 구현하고 리셋 UI/버튼은 만들지 않았다.
3. **점수 표시 형식**: 천 단위 구분 기호 등 표시 포맷 요구사항이 없어 `ToString()` 그대로 사용했다(4-3절, 4-4절).
4. **NEW RECORD 연출의 구체적 형태**: 신기록 시 `IsNewHighScore`를 활용해 별도 표시를 넣기로는 확정됐다(0-1절 참고). 다만 애니메이션·사운드·색상 등 구체적 연출 형태는 지정된 바 없다. 이 계획은 최소 구현으로, 게임오버 화면에 배지/텍스트 오브젝트 하나를 두고 `IsNewHighScore`가 true일 때만 `SetActive(true)`하는 것까지만 구현한다(4-3절). 구체적 연출(움직임·효과음 등)은 에디터에서 사용자가 직접 추가해야 한다.

### 0-1. 사용자 확인으로 확정된 사항 (최초 계획 대비 변경)

- **점수 지표**: 이동 거리가 아니라 **생존시간**(경과 시간)으로 확정. Feature "점수 로컬 저장" Task 1의 예전 본문("주행 거리 기반")보다 Feature "점수 집계 관련 데이터 테이블" Task의 "생존시간" 쪽이 실제 의도였다. 거리 기반 계산(수평 이동량 누적)은 전부 제거하고 `Time.deltaTime` 누적으로 대체한다(4-2절).
- **가중치 수치**: 생존 1초당 1점, 사과 섭취 시 30점, 치즈 섭취 시 60점으로 확정(임시 밸런싱 값이며 플레이테스트로 조정 가능, 4-1절 `ScoreData`).
- **실시간 점수 표시**: 게임오버 화면뿐 아니라 플레이 중에도 상시 보이는 점수 HUD가 필요하다. 신규 `ScoreHUD.cs`로 구현한다(4-4절).
- **신기록 연출**: `IsNewHighScore`를 실제로 활용해 게임오버 화면에 신기록 여부를 표시한다. 구체적 형태는 여전히 미확정이다(위 0-4번 참고).

## 1. 코드베이스 조사 결과

### 1-1. 게임오버 트리거 확인 (`CatController.cs`, `GameOverUI.cs`)
- `Assets/02_Scripts/Cat/CatController.cs`: `public event Action OnPlayerCaught;`가 `OnTriggerEnter`에서 플레이어와 충돌한 순간(Caught 상태 진입) 한 번 발생한다. 이미 `GameOverUI`가 이 이벤트 하나만 구독 중이며, 멀티캐스트 델리게이트라 추가 구독자를 얼마든지 더 붙일 수 있음을 확인했다.
- `Assets/02_Scripts/Game/GameOverUI.cs`: `HandlePlayerCaught()`에서 `_gameOverPanel.SetActive(true)`만 수행한다. 점수 관련 코드는 전혀 없다. 이번 계획은 이 파일을 수정하지 않고, 점수 확정·표시 로직을 별도 컴포넌트로 분리해 같은 `OnPlayerCaught`(또는 그로부터 파생된 이벤트)를 독립적으로 구독하게 한다.
- **주의**: `GameOverUI`와 신규 `ScoreController`가 **둘 다** `CatController.OnPlayerCaught`를 직접 구독하면, 어느 쪽 핸들러가 먼저 실행될지는 구독 순서(스크립트 실행 순서·씬 배치 순서)에 좌우되어 보장되지 않는다. `ScoreResultUI`가 만약 `CatController.OnPlayerCaught`를 직접 구독해 `ScoreController.HighScore`를 읽는다면, `ScoreController` 자신의 핸들러보다 먼저 실행될 경우 **최고기록이 갱신되기 전(stale) 값을 읽는 경쟁 상태**가 생길 수 있다. 이 문제를 피하기 위해 `ScoreResultUI`는 `CatController.OnPlayerCaught`를 직접 구독하지 않고, `ScoreController`가 최고기록 비교·저장까지 끝낸 뒤에만 발생시키는 자체 이벤트(`OnScoreFinalized`)를 구독하도록 설계했다(4-2·4-3·6-4절 근거).

### 1-2. 음식 소비 이벤트 확인 (`Food.cs`, `IHungerObj.cs`, `ObjectSpawner.cs`)
- `Assets/02_Scripts/Hunger/Food.cs`: `public event Action<Food> OnConsumed;`는 **인스턴스별** 이벤트다. `Assets/02_Scripts/Spawn/ObjectSpawner.cs`를 보면 `SpawnFood()`에서 풀에서 꺼낼 때마다 `food.OnConsumed += HandleFoodConsumed;`로 개별 구독하고, `DespawnFood()`에서 반환할 때 해제하는 패턴을 쓴다(39·263·279행). 즉 **스폰 시점을 아는 컴포넌트만** 개별 `Food` 인스턴스를 구독할 수 있고, 스폰 시점 정보는 오직 `ObjectSpawner` 내부(`_activeFoods` 딕셔너리, 전부 `private`)에만 있다.
- `IHungerObj.cs`: `HungerObjType`(Obstacle/Apple/Cheese)과 `Amount`를 노출한다. 인터페이스 주석에 "종류 구분이 필요한 다른 Feature(예: 점수 시스템)가 GetComponent로 이 인터페이스를 얻어 읽을 수 있다"고 명시되어 있어, 이번 계획이 `HungerObjType`을 읽는 것은 이 인터페이스가 원래 의도한 용도와 일치한다.
- 결론: `ObjectSpawner.cs`를 수정하지 않고 점수 시스템이 "어떤 음식이 언제 소비됐는지"를 알려면, `Food.cs`에 **정적(static) 이벤트**를 하나 추가하는 것이 가장 작은 변경이다. 인스턴스 이벤트(`OnConsumed`, 풀 반환용)는 그대로 두고, 같은 트리거 지점에서 정적 이벤트를 함께 발생시키면 스폰/풀 관리와 무관하게 "이 씬에서 소비되는 모든 음식"을 전역에서 구독할 수 있다(3절, 6-1절 근거). 이 변경은 `Food.cs`(사용자 소유 파일)에 대한 수정이므로 **실제 구현 전 사용자 확인이 필요**하다(CLAUDE.md 파일 수정 규칙).

### 1-3. 삭제된 오도미터 관련 확인, 그리고 생존시간 채택으로 인한 추가 단순화
- 두 파일을 전문 읽었다. 현재 `PlayerPathRecorder`는 경로점 큐(`Queue<Vector3>`)만 관리하고, `CatController`는 `Vector3.Distance` 기반 직선거리(`Gap`)만 계산한다. 누적 이동 거리를 저장하는 필드는 어디에도 없음을 확인했다 — 전달받은 이력(오도미터 삭제)과 일치한다.
- 사용자 확인으로 점수 지표가 거리 대신 생존시간으로 확정되면서(0-1절), `ScoreController`는 애초에 플레이어 위치를 전혀 추적할 필요가 없어졌다 — `Update()`에서 `Time.deltaTime`만 누적하면 되므로, `PlayerPathRecorder`/`CatController`의 오도미터 삭제 이력과 다시 엮일 여지 자체가 설계상 사라졌다.

### 1-4. 데이터 테이블 컨벤션 확인 (`PlayerStatData`, `CatStatData`, `ObjectSpawnData`, `SpeedEffectData`)
- 4개 파일 모두 `[CreateAssetMenu(fileName = "...", menuName = "MouseAndCheese/...")]`가 붙은 `ScriptableObject`이며, `[SerializeField] private` 필드 + `public` 읽기전용 프로퍼티로만 값을 노출하는 동일한 패턴을 따른다. 클래스 주석에 공통적으로 "정식 수치는 데이터 테이블 Feature에서 확정한다"는 임시 스텁 문구가 있다. 에셋 실체는 전부 `Assets/05_Data/*.asset`에 있다.
- 이번 계획의 `ScoreData`도 동일 패턴·동일 폴더 컨벤션을 따른다.

### 1-5. 로컬 저장 방식 검토
- 프로젝트 전체에서 `PlayerPrefs` 사용처가 전혀 없음을 확인했다(신규 도입). 다만 UniTask/Addressables처럼 "프로젝트 규모에 비해 과한 외부 인프라"를 도입했다가 되돌린 이력이 있다는 점을 고려하면, Unity 내장 API인 `PlayerPrefs`(패키지 추가 불필요, 동기 호출, 로컬 key-value 저장)가 "로컬 최고기록 1개 정수값 저장"이라는 요구사항에 가장 가볍고 적합하다고 판단했다. JSON 파일 직접 관리, 별도 세이브 매니저 클래스 등은 이번 요구사항(정수 하나) 대비 과설계로 보여 채택하지 않았다(6-5절 근거).

### 1-6. 씬 계층 구조 확인 (`Assets/01_Scenes/02_Ingame.unity`)
- `GameOver` 패널(`m_IsActive: 0`, 초기 비활성)의 자식은 `Re_Button`, `Quit_Button` 2개뿐이며 점수 표시용 텍스트 오브젝트는 없다 — 신규로 만들어야 한다.
- `ObjectSpawner`는 `Kitchen`이라는 씬 루트 오브젝트(NavMeshSurface와 함께)에 부착되어 있고, `Player`/`Cat`은 각각 별도 프리팹 인스턴스로 씬에 배치되어 있다. `GapDistanceUI`(Canvas 하위 TMP 텍스트)가 `_catController` 필드로 씬의 `Cat` 인스턴스를 직접 참조하는 것을 확인했다 — **서로 다른 프리팹 인스턴스끼리 씬 레벨에서 인스펙터로 직접 교차 참조하는 것이 이 프로젝트의 표준 패턴**이다(`CatController._player`/`_pathRecorder` 필드도 동일한 방식). 이번 계획의 `ScoreController._catController`, `ScoreHUD._scoreController`, `ScoreResultUI._scoreController` 필드도 같은 패턴을 그대로 따른다.
- `Canvas` 하위에는 `HungerGaugeUI`(Slider)와 `GapDistanceUI`(TMP 텍스트)가 이미 항상 활성 상태로 올라가 있다 — 실시간 점수 HUD가 필요해지면서(0-1절), 신규 `ScoreHUD`도 이 두 컴포넌트와 같은 자리(Canvas 루트)에 올려 동일한 "항상 활성" 패턴을 따른다.
- 모든 참조는 `[SerializeField]` 인스펙터 직결이며, DI 프레임워크·Singleton·ServiceLocator는 프로젝트 전역에 없다.

### 4-2. `ScoreController.cs` (신규)

```csharp
using System;
using UnityEngine;

/// <summary>
/// 생존시간과 음식 섭취를 합산해 점수를 계산하고, 게임오버 시 로컬 최고기록을 갱신·저장하는 클래스. Player GameObject에 부착한다
/// </summary>
public class ScoreController : MonoBehaviour
{
    private const string HighScoreKey = "MouseAndCheese_HighScore";

    [SerializeField] private CatController _catController;
    [SerializeField] private ScoreData _scoreData;

    private float _rawScore;
    private int _highScore;
    private bool _isGameOver;

    /// <summary>
    /// 점수가 확정(게임오버, 최고기록 비교·저장 완료)되면 한 번 발생하는 이벤트
    /// </summary>
    public event Action OnScoreFinalized;

    /// <summary>
    /// 지금까지 누적된 점수(정수로 반올림)
    /// </summary>
    public int CurrentScore => Mathf.RoundToInt(_rawScore);

    /// <summary>
    /// 로컬에 저장된 최고기록
    /// </summary>
    public int HighScore => _highScore;

    /// <summary>
    /// 이번 판 점수가 최고기록을 갱신했는지 여부(게임오버 확정 후에만 유효)
    /// </summary>
    public bool IsNewHighScore { get; private set; }

    /// <summary>
    /// 저장된 최고기록을 불러온다
    /// </summary>
    private void Awake()
    {
        _highScore = PlayerPrefs.GetInt(HighScoreKey, 0);
    }

    /// <summary>
    /// 포획 이벤트와 음식 소비 이벤트를 구독한다
    /// </summary>
    private void OnEnable()
    {
        _catController.OnPlayerCaught += HandlePlayerCaught;
        Food.OnAnyConsumed += HandleFoodConsumed;
    }

    /// <summary>
    /// 이벤트 구독을 해제한다
    /// </summary>
    private void OnDisable()
    {
        _catController.OnPlayerCaught -= HandlePlayerCaught;
        Food.OnAnyConsumed -= HandleFoodConsumed;
    }

    /// <summary>
    /// 게임오버 전까지 매 프레임 생존시간을 점수에 누적한다
    /// </summary>
    private void Update()
    {
        if (_isGameOver)
        {
            return;
        }

        _rawScore += _scoreData.SurvivalScorePerSecond * Time.deltaTime;
    }

    /// <summary>
    /// 소비된 음식이 사과·치즈면 해당 보너스를 점수에 더한다. 장애물은 점수에 영향을 주지 않는다(0절 근거)
    /// </summary>
    private void HandleFoodConsumed(Food food)
    {
        if (_isGameOver)
        {
            return;
        }

        switch (food.HungerObjType)
        {
            case HungerObjType.Apple:
                _rawScore += _scoreData.AppleScoreBonus;
                break;
            case HungerObjType.Cheese:
                _rawScore += _scoreData.CheeseScoreBonus;
                break;
        }
    }

    /// <summary>
    /// 점수 누적을 멈추고, 최고기록을 갱신했다면 저장한 뒤 확정 이벤트를 발생시킨다
    /// </summary>
    private void HandlePlayerCaught()
    {
        _isGameOver = true;
        IsNewHighScore = CurrentScore > _highScore;
        if (IsNewHighScore)
        {
            _highScore = CurrentScore;
            PlayerPrefs.SetInt(HighScoreKey, _highScore);
            PlayerPrefs.Save();
        }

        OnScoreFinalized?.Invoke();
    }
}
```

using TMPro;
using UnityEngine;

/// <summary>
/// 게임오버 시 이번 판 점수와 최고기록을 TMP 텍스트에 표시하고, 신기록이면 배지를 노출하는 클래스. 항상 활성 상태인 오브젝트(Canvas)에 부착한다

### 4-5. `Food.cs` 수정안 (기존 파일, 사용자 확인 후 적용)

```csharp
using System;
using UnityEngine;

public class Food : MonoBehaviour, IHungerObj
{
    public HungerObjType HungerObjType => _type;
    public float Amount => _amount;
    [SerializeField] private float _amount;
    [SerializeField] private HungerObjType _type;

    /// <summary>
    /// 플레이어에게 소비되어 배고픔 변경이 적용된 직후 발생하는 이벤트(오브젝트 풀 반환 트리거)
    /// </summary>
    public event Action<Food> OnConsumed;

    /// <summary>
    /// 어떤 Food 인스턴스든 소비되면 함께 발생하는 정적 이벤트(점수 등 전역 구독자용)
    /// </summary>
    public static event Action<Food> OnAnyConsumed;

    /// <summary>
    /// 플레이어(HungerController)와 닿으면 배고픔 변경을 적용하고 소비 이벤트를 발생시킨다
    /// </summary>
    private void OnTriggerEnter(Collider other)
    {
        if(other.TryGetComponent(out HungerController hungerController))
        {
            hungerController.ChangeHunger(_amount);
            OnConsumed?.Invoke(this);
            OnAnyConsumed?.Invoke(this);
        }
    }
}
```

## 6. 주의 사항 및 설계 결정 근거

1. **`ObjectSpawner.cs`를 수정하지 않고 `Food.cs`에 정적 이벤트를 추가하는 쪽을 선택**: 점수 시스템이 음식 소비를 감지하려면 스폰된 `Food` 인스턴스를 알아야 하는데, 그 정보는 현재 `ObjectSpawner`의 `private` 필드에만 있다(1-2절). `ObjectSpawner`에 공개 이벤트를 추가해 중계하는 방법도 있었지만, 이미 복잡한 풀링·만료(cheese lifetime) 로직을 가진 파일을 건드리기보다, `Food` 자신이 "누구든 소비되면 알림"을 정적 이벤트로 내보내는 쪽이 더 단순하고 `ObjectSpawner`의 책임(생성·회수)과 점수 계산(집계)을 깔끔히 분리한다.
2. **점수 표시를 `GameOverUI.cs` 수정이 아니라 별도 `ScoreResultUI` 컴포넌트로 분리**: `GameOverUI`는 이미 패널 활성화·재시작·종료라는 명확한 책임을 갖고 있다. `CatController.OnPlayerCaught`가 멀티캐스트 이벤트라 여러 구독자를 허용한다는 점(1-1절)을 활용해, 점수 표시라는 별개 관심사를 독립 컴포넌트로 분리했다. 이렇게 하면 `GameOverUI.cs` 수정에 대한 사용자 확인 절차 자체가 필요 없어진다.
3. **`ScoreHUD`가 이벤트 대신 매 프레임 폴링으로 텍스트를 갱신**: 점수는 `Update()`에서 매 프레임 계속 바뀌는 값이라, 값이 바뀔 때마다 이벤트를 발생시키면 매 프레임 이벤트를 쏘는 셈이라 비효율적이다. 이미 같은 패턴을 쓰는 `GapDistanceUI`(매 프레임 `CatController.Gap`을 읽어 바뀐 경우에만 텍스트 갱신)를 그대로 따라, `ScoreHUD`도 이벤트 없이 `ScoreController.CurrentScore`를 매 프레임 읽고 바뀐 경우에만 텍스트를 갱신한다(1-6절 근거). 게임오버 후 `_isGameOver`가 true가 되어 점수가 더는 바뀌지 않아도, 폴링이라 마지막 값이 자연스럽게 화면에 남는다.
4. **`ScoreResultUI`가 `CatController.OnPlayerCaught`를 직접 구독하지 않고 `ScoreController.OnScoreFinalized`를 구독**: 1-1절에서 설명한 대로, 같은 소스 이벤트(`OnPlayerCaught`)에 `ScoreController`와 `ScoreResultUI`가 동시에 독립 구독하면 어느 쪽이 먼저 실행되는지 보장되지 않아, `ScoreResultUI`가 최고기록 갱신 **이전** 값을 읽는 경쟁 상태가 생길 수 있다. `ScoreController`가 최고기록 비교·저장까지 마친 뒤에만 `OnScoreFinalized`를 발생시키고 `ScoreResultUI`는 그 이벤트만 구독하게 함으로써, 구독 순서와 무관하게 항상 올바른 최종값을 읽도록 구조적으로 보장했다. 이 설계가 성립하려면 `ScoreResultUI`가 게임오버 시점 이전에 이미 구독을 마친 상태여야 하므로, **시작 시 비활성인 `GameOver` 패널 하위가 아니라 항상 활성 상태인 오브젝트에 부착**해야 한다(4-6절 5항).
5. **최고기록 저장에 `PlayerPrefs` 사용**: 이 프로젝트가 과거 UniTask/Addressables 같은 외부 인프라를 "규모에 비해 과하다"는 이유로 되돌린 이력을 고려해, 정수값 1개("최고 점수")를 저장하는 데는 Unity 내장 `PlayerPrefs`면 충분하다고 판단했다(1-5절). 별도의 JSON 직렬화·세이브 매니저 클래스는 이번 범위(정수 1개)에는 과설계로 보여 채택하지 않았다.
6. **점수 계산에 위치 추적이 전혀 필요 없어짐**: 지표가 생존시간으로 확정되면서(0-1절), `ScoreController`는 `_lastPosition` 같은 위치 관련 필드를 아예 갖지 않는다. 과거 갭 계산용 오도미터가 "죽은 코드"로 판단되어 삭제된 이력(1-3절)과 다시 엮일 여지가 설계 단계에서부터 없다.
7. **`ScoreData`를 `PlayerStatData`/`CatStatData`/`ObjectSpawnData`/`SpeedEffectData`와 동일한 ScriptableObject 임시 스텁 패턴으로 설계**: 프로젝트 전역에서 반복적으로 채택된 패턴이며(1-4절), "데이터 테이블" Feature가 나중에 정식 수치로 흡수하기 쉽다.
8. **`Food.cs`를 제외한 기존 파일(`CatController.cs`, `GameOverUI.cs`, `HungerController.cs`, `ObjectSpawner.cs`, `PlayerPathRecorder.cs`)을 전혀 수정하지 않음**: 전부 기존 공개 API(`OnPlayerCaught`, `IHungerObj.HungerObjType`)만으로 요구사항을 충족할 수 있었다. `Food.cs`의 정적 이벤트 추가 1건만 예외이며, 이 역시 기존 동작을 바꾸지 않는 순수 추가(additive) 변경이다.
9. **코딩 컨벤션 준수**: 모든 필드/메서드에 접근 제어자 명시, `var` 미사용, `!` 대신 조건식 사용(단일 부정 케이스 없음), 클래스·public 멤버에 한국어 `<summary>` XML 주석 작성, 람다식 미사용, 디버깅 목적의 null 체크 없음(`_catController`/`_scoreData` 등 필수 참조 미연결 시 `NullReferenceException`이 그대로 발생하는 fail-fast 방식 — `HungerController`/`GameOverUI`의 기존 결정과 동일).
