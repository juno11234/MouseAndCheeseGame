# 음식·장애물 랜덤 생성 (System: 음식·장애물 랜덤 생성 / Feature: NavMesh 위 랜덤 스폰 · 오브젝트 풀) 구현 계획

- 작성 날짜: 2026-09-20 (26_0920)
- 작성자: planner (Claude Code)
- 요청 범위: Notion GDD "음식·장애물 랜덤 생성"(중요도 상)의 Task 4개 전부가 이번 범위다. Notion은 접근하지 않고 사용자가 프롬프트로 전달한 요약을 근거로 삼았다. 최초 요청 3가지(1~3)에 이어 `!주석`으로 사용자가 확정한 내용(4~9)이 반영된 버전이다.
  1. **음식·장애물을 랜덤으로 생성한다.**
  2. **생성/제거는 오브젝트 풀(Object Pool)을 활용한다.** Unity 내장 `ObjectPool<T>`를 쓰고, 종류별 동시 존재 상한으로 개수를 제한한다(0-10).
  3. **NavMesh가 Bake된 곳에서만 생성한다.**
  4. **생성 위치는 높이 구간으로 정한다.** 일정 Y 높이 이상은 생성 확률이 올라가고, 일정 Y 높이 구간은 생성을 제한한다(0-5). 이것이 GDD 4번 Task(위쪽 경로 스폰 밀도)의 구현 방식이다(0-12).
  5. **생성 시점**: 시작 시 5개 정도를 한꺼번에 만들고 이후로는 지속적으로 생성한다. 위치 조건은 플레이어와의 거리만 확인한다(고양이는 보지 않는다, 0-4).
  6. **오브젝트를 먹으면 풀로 회수한다**(0-9).
  7. **쥐덫은 치즈와 무관하게 계속 생성한다.** 치즈를 소환할 때는 치즈로부터 정해진 최소 간격만큼 떨어진 곳에 동반 쥐덫도 함께 만든다(0-8).
  8. **이벤트는 `System.Action`으로 선언하고 기존 커스텀 델리게이트도 `Action`으로 바꾼다**(0-11).
  9. 수량·확률·간격·회복량·치즈 수명 같은 수치는 사용자가 플레이하며 밸런스를 보고 정한다. 이 계획의 수치는 전부 임시값이다(0-6, 0-7, 0-13).
- 함께 구현하는 GDD Task: (1) 사과는 생성 빈도가 높고 치즈는 낮음, (2) 치즈는 항상 쥐덫과 함께 소환, (3) 모든 오브젝트는 서로 최소 거리를 두고 생성, (4) 점프대(현재는 풀잎 비행 기믹) 위쪽(싱크대 등) 경로에 음식 스폰 밀도를 지상보다 높게(0-5의 높이 구간 방식). 구체 수치는 사용자가 밸런스를 보며 정하므로 0절에 임시값으로 두었다.
- 배경(기획 의도 요약): 매 판 다른 경로 경험으로 반복 플레이의 지루함을 막고, 사과·치즈 배치로 "위험과 보상의 선택"을 구현한다. 치즈 근처엔 항상 쥐덫이 함께 생성되고, 치즈는 사과보다 훨씬 드물며 일정 시간 뒤 사라진다. 음식은 서로 일정 거리를 두고 생성된다. 배치 밀도가 배고픔 소모 속도와 고양이 추격 갭 관리 난이도를 사실상 결정하며, 특정 구간에 몰려 불공평하게 배치되는 것이 위험 요소다.
- 범위 밖으로 명시하는 것
  - **데이터 테이블 정식 구현**: 별도 Feature "음식 장애물 생성 관련 데이터 테이블"의 책임이다. 이번에는 `CatStatData`/`LeafFlightData` 선례처럼 필요한 수치를 담는 임시 스텁 ScriptableObject(`ObjectSpawnData`)까지만 만든다.
  - **점수·랭킹, 게임오버/리스타트, 음식 섭취 연출·이펙트, 치즈 만료 연출(깜빡임 등)**: 구현하지 않는다.
  - **사과 만료, 플레이어 뒤로 멀어진 오브젝트 회수**: 사용자가 정하지 않아 넣지 않았다(0-9).
  - **고양이·플레이어 도달 가능성 필터**: 사용자가 높이 구간으로 정하기로 했으므로 넣지 않았다(0-5).
- 범위에 포함하는 "반드시 함께 바뀌어야 하는 부분"
  - **소비 시 풀로 반환하는 계약(리뷰 R5)**: 풀은 "쓰인 오브젝트가 언제 돌아오는가"를 알아야 하는데 현재 `Food`에는 소비 통지가 없다. 그래서 `Food`에 소비 이벤트를 추가한다(3절). 이 변경 없이는 풀 반환 지점이 존재하지 않는다.
  - **`Apple_Obj.prefab`에 `Food` 컴포넌트 부착**: 리뷰가 지적한 대로 사과 프리팹에는 `Food`가 없어 먹어도 효과가 없고 소비 이벤트도 발생하지 않는다(에디터 작업, 4-6절).
  - **기존 이벤트의 `Action` 전환**(사용자 지시): `Player`, `CatController`, `InputManager`, `HungerController`의 델리게이트 선언을 삭제하고 이벤트 타입만 `Action`으로 바꾼다(1-11절, 4-4절). 동작은 바뀌지 않는다.
- 인접 Feature와의 경계(이번 계획에서 직접 구현하지 않음)
  - **데이터 테이블 Feature**: 오브젝트별 회복량·데미지량, 스폰 확률·최소 간격의 정식 값과 에셋은 그쪽 책임이다. `ObjectSpawnData`는 그 전까지의 자리 표시자이며, 그 Feature가 이 필드 계약(이름, 의미)을 이어받아 정식화한다.
  - **점수·랭킹 Feature**: 사과/치즈 구분이 필요하면 `Food.OnConsumed`(`Action<Food>`)를 구독해 `food.HungerObjType`을 읽으면 된다. 이 이벤트는 그 용도로도 쓸 수 있게 종류 정보를 가진 `Food`를 그대로 넘긴다(26_0915 계획 6-12절의 미해결 항목이 부분 해소됨). 이번 계획은 점수 코드를 만들지 않는다.
  - **맵 시스템(풀잎 비행) Feature**: `LeafFlightTrigger`, `PlayerPathRecorder`는 수정하지 않는다. `Player`, `CatController`는 이벤트 `Action` 전환(3절)만 수정한다. 고양이·플레이어 경로 기록과 이번 스포너 사이에는 데이터 의존이 없다.

## 0. 결정 사항과 아직 확정되지 않은 사항

0-1~0-4, 0-5(방식), 0-9(섭취 시 회수), 0-10, 0-11, 0-12는 사용자가 확정한 사항이다. 수치(0-5의 높이 값, 0-6, 0-7, 0-8의 쥐덫 값, 0-13)는 사용자가 플레이하며 밸런스를 보고 정할 예정이라 임시값을 두었다. 사용자가 확정하지 않은 항목은 추측으로 결정하지 않고 사실, 위험, 코드에 넣은 임시 처리, 결정 후보를 적었다. 임시 처리는 4절 코드에 반영돼 있다. 수치는 전부 개발 테스트용 자리 표시자이며 `ObjectSpawnData` 한 곳에서 바꾼다.

### 0-1. 음식·장애물 랜덤 생성 — 확정

- 사용자 결정: 오브젝트(음식·장애물)를 랜덤으로 생성하는 로직을 만든다. 이 계획의 대상 프리팹은 `Assets/4_Prefabs/Obj/`의 `Apple_Obj.prefab`, `Cheese_Obj.prefab`, `Trap_Obj.prefab` 세 개다(1-2절). `Assets/4_Prefabs/` 바로 아래의 `Apple.prefab`, `Cheese.prefab`, `trap.prefab`은 위 세 Obj 프리팹의 자식 비주얼(중첩 프리팹 원본)로만 쓰이며 스포너가 직접 다루지 않는다.

### 0-2. 생성/제거는 오브젝트 풀 — 확정 (구현체 선택은 0-10에서 미확정)

- 사용자 결정: 생성과 제거를 오브젝트 풀로 한다. 즉 런타임에 `Instantiate`/`Destroy`를 반복하지 않고 비활성 인스턴스를 재사용한다.

### 0-3. NavMesh가 Bake된 곳에서만 생성 — 확정 (정확한 범위는 0-5에서 미확정)

- 사용자 결정: 생성 위치는 반드시 베이크된 NavMesh 위여야 한다. 이 계획은 후보 지점을 NavMesh 삼각형에서 뽑고 `NavMesh.SamplePosition`으로 한 번 더 확인해 그 위 좌표만 쓴다(4-2절). NavMesh가 없거나 비어 있으면 아무것도 생성하지 않는다.

### 0-4. 생성 영역과 타이밍 — 확정 (전체 NavMesh 대상, 시작 시 5개 정도 일괄 + 이후 지속 생성, 위치 조건은 플레이어와의 거리만)

- 사용자 결정: 시작 시 5개 정도를 한꺼번에 만들고, 이후로는 지속적으로 생성한다. 위치 조건으로는 플레이어와의 거리만 확인한다(고양이 위치는 보지 않는다).
- 사실: 현재 맵은 X -50~0, Z 0~50, 약 50m x 50m의 닫힌 방(바닥 Plane + 벽 4면 + 천장 y=28)이다(1-6절). 플레이어의 전진 방향은 고정 축이 아니라 카메라 방향(`CameraController.ForwardDirection`)이라 "앞쪽 일정 범위" 같은 기준을 세우기 어려워 방 전체 NavMesh를 대상으로 한다.
- 구현: `Start`에서 `_initialSpawnAttempts`(임시 5)번 생성을 시도하고, 이후 `_spawnInterval`초마다 한 번씩 생성을 시도한다. 종류별 동시 존재 상한(0-6)에 닿으면 그 틱은 건너뛴다. 위치 검증에서 플레이어와의 최소 거리(`_minDistanceFromPlayer`)를 확인한다. 고양이 위치는 보지 않는다.
- 해석(확인 필요): (a) "5개 정도"는 **생성 시도 5회**로 구현했다. 위치를 못 찾으면(상한, 최소 간격, 플레이어 거리 조건) 5개보다 적을 수 있다. 정확히 5개여야 한다면 알려주면 성공할 때까지 반복하도록 바꾼다. (b) "플레이어와의 거리만 체크"는 영역·기준점 선택(플레이어 앞쪽 범위, 고양이와의 거리 등)에 대한 결정으로 해석했고, GDD Task 3(오브젝트끼리 최소 거리)의 간격 확인(0-7)은 그대로 유지했다.
- 위험(코드로 막지 않음): 시작 일괄 뒤 지속 생성만 하고 플레이어 뒤로 멀어진 오브젝트는 회수하지 않는다(0-9). 방이 좁은 지금은 문제가 아니지만 맵이 커지면 필요해진다.

### 0-5. "NavMesh가 Bake된 곳"의 범위와 높이 구간 — 방식 확정, 수치는 임시

- 사용자 결정: 높이 구간으로 정한다. **일정 Y 높이 이상은 생성 확률이 올라가고, 일정 Y 높이는 생성을 제한한다.** 이 결정이 GDD 4번 Task(위쪽 경로 스폰 밀도)의 구현 방식이 된다(0-12).
- 사실(1-5절): `NavMeshSurface`는 1개(`Kitchen` 오브젝트, 렌더 메시 수집)이고 베이크 데이터는 `NavMesh-Kitchen.asset`이다. 에이전트 타입은 Humanoid(ID 0) 하나뿐이다. NavMeshLink는 씬에 10개이고 전부 Area 2(Jump), 양방향이다. NavMeshLink는 삼각형이 아니라 오프메시 연결이라 스폰 후보가 되지 않고, 링크 양 끝점이 놓인 표면(바닥과 가구 위)은 NavMesh 다각형이라 후보에 포함된다. 베이크 데이터가 바이너리라 **가구 위에 실제로 어떤 NavMesh 표면이 얼마나 있는지는 이 환경에서 확인하지 못했다([검증 필요])**.
- 구현(4-1, 4-2절)
  1. 후보 지점을 NavMesh 삼각형에서 뽑을 때 삼각형 **무게 중심의 월드 Y**로 가중치를 정한다. 제한 구간 안이면 제외(가중치 0), `_elevatedHeight` 이상이면 면적에 `_elevatedWeightMultiplier`를 곱하고, 그 외에는 면적 그대로다.
  2. `NavMesh.SamplePosition`으로 스냅한 **최종 Y도 제한 구간 밖인지 확인**한다(경사면·큰 삼각형의 무게 중심 근사 오차 보정). 쥐덫 링 배치에도 같은 확인이 적용된다.
  3. 확률 상승은 "높은 표면이 뽑힐 확률"(면적 가중치)로 표현했고 사과·치즈·쥐덫에 공통으로 적용된다.
- 미확정 (임시 처리)
  1. **Y 임계값과 배율 수치**: `_elevatedHeight` 1, `_elevatedWeightMultiplier` 3. 지면 NavMesh 표면은 약 0.1~0.16m(고양이 시작 Y 0.16으로 추정), 가구 위는 그보다 높다고 추정한다([검증 필요]). 수치는 씬 뷰에서 가구 위 NavMesh 높이를 보고 사용자가 정한다.
  2. **"일정 Y 높이는 생성 제한"의 형태**: 구간(최소~최대)인지 상한(이상 금지)인지 사용자가 말하지 않았다. 임시 = 구간 `[_restrictedMinHeight, _restrictedMaxHeight]`이고 `_restrictHeight`를 false로 두어 **기본은 꺼져 있다**(값이 정해지기 전에 임의 구간이 생성을 막지 않도록). 상한 방식이면 최대값을 크게 잡으면 같은 표현이 된다.
  3. **확률 상승을 치즈·쥐덫에도 적용할지**: 임시 = 공통 적용(샘플러 하나를 세 종류가 공유). 종류별로 다르게 하려면 샘플러를 종류별로 나눠야 한다.
  4. **도달 가능성 필터(고양이·플레이어)**: 넣지 않았다. 가구 위 NavMesh 중 링크로 이어지지 않은 곳이나 고립 섬이 후보에 들 위험이 남는다(높이 제한 구간으로 일부 대응 가능).
  5. **Area/에이전트 타입**: `_areaMask`(기본 `NavMesh.AllAreas`), `_agentTypeId`(기본 0)로 좁힐 수 있게 열어 두었다.
- 위험: (a) 삼각형 무게 중심 기준이라 높이가 걸쳐 있는 경사면·큰 삼각형은 근사다. (b) 바닥 면적이 압도적이라 배율이 낮으면 위쪽 밀도 상승이 체감되지 않는다. (c) 삼각형 높이와 `SamplePosition` 높이의 차이는 검증하지 못했다.

### 0-6. 동시 존재 최대 수 — 구조 확정(종류별 상한), 수치는 밸런스를 보며 결정, 임시 처리 = 사과 20, 치즈 2, 쥐덫 6

- 사용자 결정: 종류별 상한으로 개수를 제한한다(0-10). 수치는 밸런스를 보며 정한다.
- 사실: 풀 크기는 종류별 동시 존재 상한과 같게 둔다. `PlayerStatData.asset` 기준 `MaxHunger` 50, 초당 감소 2(만복에서 약 25초 후 0), 이동 속도 2~10m/s다. 사과 회복량은 정해지지 않았다(0-13).
- 위험: 밀도가 너무 낮으면 무작위로 달리는 플레이어가 사과를 거의 만나지 못한다. **추정**: 바닥 약 2,500m²에 사과 20개면 밀도 약 0.008개/m²이고, 폭 약 0.8m로 10m/s 이동하는 플레이어가 훑는 면적은 초당 약 8m²라 목표 없이 달리면 약 15초에 1개 수준이다(가구 표면적과 벽·가구 점유 면적은 계산에서 제외). 반대로 너무 높으면 배고픔이 무의미해진다. 이 수치는 미검증이며 플레이테스트가 필요하다.
- 임시 처리: `ObjectSpawnData`의 `_maxActiveApples` 20, `_maxActiveCheeses` 2, `_maxActiveTraps` 6. 쥐덫 상한은 독립 쥐덫과 치즈 동반 쥐덫을 합친 값이다(0-8).

### 0-7. 사과·치즈·쥐덫 생성 확률, 생성 주기, 최소 간격 수치 — 수치는 밸런스를 보며 결정, 임시 처리 = 가중치 9:1:2, 주기 1초, 오브젝트 간 4m, 플레이어와 6m

- 사용자 결정: 밸런스를 보며 정한다.
- 사실: "사과는 빈도가 높고 치즈는 낮다", "오브젝트끼리 서로 최소 거리를 둔다(겹치지 않을 정도)", "음식은 서로 일정 거리를 둔다"만 정해졌고 수치는 없다. 기획 문구 "겹치지 않을 정도"와 "일정 거리를 두고 생성"은 요구하는 간격 크기가 다르다(전자는 사실상 콜라이더 크기, 후자는 경로 계획용 간격).
- 위험: 간격이 너무 작으면 몰림 위험(GDD의 불공평한 배치)이 커지고, 너무 크면 상한만큼 배치되지 못해 스폰 시도가 계속 실패한다.
- 임시 처리: `_appleSpawnWeight` 9, `_cheeseSpawnWeight` 1, `_trapSpawnWeight` 2(생성 틱마다 가중치로 종류 결정), `_spawnInterval` 1초, `_initialSpawnAttempts` 5(0-4), `_minObjectDistance` 4m(모든 오브젝트 쌍, 3D 거리), `_minDistanceFromPlayer` 6m, 위치 탐색 최대 시도 `_maxPlacementAttempts` 10. 최소 간격 판정은 종류 구분 없이 하나의 값이다. 치즈와 자신의 동반 쥐덫 쌍은 0-8의 별도 거리 규칙을 따르고 이 값에서 제외한다.
- 결정 후보: 종류 쌍별 최소 간격 표(사과-사과, 사과-치즈, 치즈-쥐덫 …) / 확률을 가중치 대신 종류별 독립 타이머로 표현 / 데이터 테이블 Feature가 확정.

### 0-8. 치즈와 쥐덫의 관계 — 배치 방식(a)와 독립 생성은 확정, 수치는 밸런스를 보며 결정, 독립 생성의 해석은 확인 필요

- 사용자 결정: (1) 쥐덫 배치는 **a방식**이다. Notion 원문 "최소 거리에"를 "치즈로부터 정해진 최소 간격만큼 떨어진 곳"으로 읽는다. (2) **쥐덫은 치즈와 무관하게 계속 생성한다.** 나머지 수치는 밸런스를 보며 정한다.
- 해석(확인 필요): "쥐덫은 치즈와 무관하게 계속 생성"을 (i) 치즈가 없어도 쥐덫이 독립적으로 계속 생성되고(가중치 `_trapSpawnWeight`), (ii) 치즈가 먹히거나 만료돼도 그 쥐덫은 남는다(수명 연동 없음)는 뜻으로 해석했다. 이에 따라 이전 버전의 임시 처리 "쥐덫은 치즈와 수명을 함께한다", "단독 쥐덫은 생성하지 않는다"를 뒤집었다. 다르게 의도했다면 알려주면 고친다. 그대로 두는 것은 "치즈는 항상 쥐덫과 함께 소환"(GDD Task 2)이며, 치즈를 소환할 때 동반 쥐덫을 함께 만드는 것도 유지한다.
- 위험(새로 생김): 쥐덫에 수명이 없어 밟히기 전까지 남으면 쥐덫 풀이 상한(`_maxActiveTraps`)까지 차고, 그 뒤에는 치즈 소환(동반 쥐덫 필요)이 계속 막혀 치즈가 생성되지 않을 수 있다. 코드로 막지 않았고 4-7절 시나리오 20으로 관찰한다.
- 임시 처리: 동반 쥐덫 위치는 치즈 위치를 중심으로 링 `[_trapMinDistanceFromCheese 1.5, _trapMaxDistanceFromCheese 3]`m 안에서 `NavMesh.SamplePosition`으로 뽑는다(min = "정해진 최소 간격", max = "근처"를 위한 임시 상한, 찾지 못하면 치즈도 생성하지 않는다). 치즈 소환은 동반 쥐덫 위치를 찾고 쥐덫 풀에 빈 자리가 있을 때만 성공한다. 치즈당 동반 쥐덫은 1개다. 독립 쥐덫은 `_trapSpawnWeight`와 `_maxActiveTraps` 상한으로 생성한다. 치즈만 수명이 있고(`_cheeseLifetime` 15초) 쥐덫·사과는 만료가 없다.
- 결정 후보(치즈 굶주림 대응): 쥐덫에도 수명 / 상한이 찼을 때 가장 오래된 쥐덫 재활용 / 동반 쥐덫 전용 자리 예약(독립 쥐덫 상한을 `MaxActiveTraps - MaxActiveCheeses`로) / 치즈가 쥐덫 없이도 생성.

### 0-9. 풀 반환 조건 — 먹으면 회수 확정, 나머지는 임시 처리

- 사용자 결정: 먹으면 풀에 회수한다.
- 사실: 리뷰 R5는 "음식·함정이 소비되지 않아 재진입마다 반복 적용된다"고 지적했고 "함정을 1회용으로 할지 쿨타임을 둘지는 기획이 결정한다"고 남겼다. 현재 `Food`는 플레이어와 닿을 때마다 `ChangeHunger`를 적용하고 자기 자신을 끄지 않는다.
- 임시 처리: 풀 반환은 (1) `Food.OnConsumed`(플레이어의 `HungerController`와 닿아 배고픔이 적용된 직후) 수신 시 — 사과·치즈·쥐덫 모두이며 쥐덫도 밟으면 1회용으로 회수하는 것은 "먹으면 회수"와 같은 규칙으로 적용한 것이다, (2) 치즈 만료 시각 도달 시(치즈만, 0-8) 두 경우만이다. 씬에 미리 놓은 풀 외 `Food`(수동 배치한 `Cheese_Obj` 2개, `Trap_Obj` 1개, 1-6절)는 구독자가 없으므로 지금 동작(반복 적용)이 그대로 유지된다. 이들을 지울지는 사용자 결정이다(4-6절).
- 위험: 쥐덫이 한 번 밟히면 사라진다(밟은 뒤 다시 위험을 회피하는 재미가 없다). 회수를 하지 않으므로 플레이어 뒤로 멀어진 오브젝트는 남는다.
- 결정 후보: 쥐덫은 쿨타임 후 재활성 / 플레이어 뒤로 N미터 이상 멀어지면 회수 / 사과 만료 시간 도입 / 소비 시 연출 후 반환.

### 0-10. 풀 구현체 — 확정: Unity 내장 `ObjectPool<T>`, 종류별 상한으로 활성 개수 제한

- 사용자 결정: Unity 내장 풀(`UnityEngine.Pool.ObjectPool<T>`)을 사용하고, 종류별 상한으로 개수를 제한한다.
- 사실: 프로젝트 Unity 버전은 6000.3.19f1이다(`ProjectSettings/ProjectVersion.txt`). `UnityEngine.Pool.ObjectPool<T>`는 Unity 2021.1부터 엔진에 포함돼 있어 추가 패키지 없이 쓸 수 있다(비교는 1-9절). 이 환경에서 컴파일해 API를 확인하지 못했으므로 생성자 인자 이름과 `CountActive` 프로퍼티는 문서 기준으로 적었다([검증 필요], 컴파일 시 이름이 다르면 그에 맞춘다).
- 구현: `ObjectPool<T>.Get()`은 풀이 비면 새 인스턴스를 무제한 만든다(`maxSize`는 보관 상한일 뿐 활성 개수 상한이 아니다). 그래서 종류별 활성 상한은 스포너가 `FoodPool.ActiveCount`로 지킨다(0-6).

### 0-11. 이벤트 선언 방식 — 확정: `System.Action`, 기존 이벤트도 함께 전환

- 사용자 결정: 이벤트를 `System.Action`으로 선언하고 기존 것들도 바꾼다.
- 범위(1-11절 표, 4-4절): 새 `Food.OnConsumed`는 `Action<Food>`로 선언한다. 기존 커스텀 델리게이트는 선언을 삭제하고 이벤트 타입만 바꾼다: `Player.OnMoveStateChanged`(`Action<PlayerMoveState>`), `CatController.OnGapChanged`(`Action<float>`)·`OnPlayerCaught`(`Action`), `InputManager.OnAutoInput`·`OnJumpInput`(`Action<bool>`), `HungerController.OnHungerChanged`(`Action<float>`). 구독·해제·호출 코드와 핸들러 시그니처는 그대로라 동작이 같다.
- 주의(6-13절): 스폰 파일은 `Random`, `Object`를 쓰므로 `using System;`을 넣지 않는다(`System.Random`, `System.Object`와 모호해짐). 전환 대상 파일에는 그런 사용이 없어 `using System;`을 추가해도 안전하다.
- `ObjectPool<T>` 생성자가 받는 콜백 인자는 이벤트가 아니라 엔진 API 시그니처(`Func`/`Action`)라 이 결정과 무관하며, 람다 없이 메서드 그룹으로 넘긴다.

### 0-12. GDD 4번 Task(위쪽 경로 스폰 밀도)를 이번 범위에 넣을지 — 확정: 포함, 0-5의 높이 구간 방식으로 구현

- 사용자 결정: 0-5의 결정과 같다. 즉 일정 Y 높이 이상 표면에서 생성 확률이 올라가는 것으로 구현한다.
- 구현: 4-2절 `NavMeshRandomPointSampler`가 삼각형 가중치에 높이 배율을 곱한다. 수치는 0-5의 임시값이다.

### 0-13. 사과 회복량, `Apple_Obj`의 `Food` 부착 — 회복량은 밸런스를 보며 결정, 임시 처리 = `_type` Apple, `_amount` 20

- 사용자 결정: 밸런스를 보며 정한다.
- 사실: `Apple_Obj.prefab`에는 `BoxCollider`(Is Trigger ON)만 있고 `Food`가 없다(1-2절). `Cheese_Obj`는 `_amount` 100/`_type` Cheese, `Trap_Obj`는 `_amount` -10/`_type` Obstacle이다. 사과 회복량은 정해지지 않았다(별도 데이터 테이블 Feature의 "오브젝트별 회복량 및 데미지량"). `Food._type`의 기본값은 열거형 첫 값 `Obstacle`이므로 컴포넌트를 새로 붙이면 반드시 `Apple`로 바꿔야 한다.
- 임시 처리: 프리팹에 `Food`를 붙이고 `_type` = Apple, `_amount` = 20을 임시로 넣는다(4-6절). 스포너는 `Food._type`에 의존하지 않고 어느 풀에서 나왔는지로 반환 대상을 결정하므로(6-3), 이 값을 실수로 잘못 넣어도 풀이 뒤섞이지 않는다.

### 1-4. 소비 계약과 풀 반환 지점 (리뷰 R5, 확장성 1), 기술 부채 4 재검증)

- 리뷰의 결론 "스폰 Feature 전에 소비 훅을 넣어 두면 스폰 쪽은 소비되면 풀 반환만 구현하면 된다"는 유효하다. 다만 훅의 위치가 `IHungerObj`/`HungerController`가 아니라 `Food`가 된다(1-1절).
- 선택: `Food`에 `public event Action<Food> OnConsumed`를 추가하고 `ChangeHunger` 직후 발생시킨다(4-4절). 이유는 6-2절. `IHungerObj`에 `Consume()`을 넣지 않은 것은 (a) 지금 `IHungerObj`를 호출하는 쪽이 없고, (b) 풀 반환은 스포너가 구독으로 처리하는 것이 이 프로젝트의 통지 방식(이벤트 + 대칭 구독)과 맞기 때문이다.
- 소비 통지는 `HungerController`에 실제로 닿은 경우에만 발생한다. 고양이의 트리거나 다른 콜라이더가 음식과 겹쳐도 `TryGetComponent<HungerController>`가 실패해 소비되지 않는다(1-8절).

### 1-7. 스폰 Y 좌표와 트리거 인식 (과거 디버깅 교훈 반영)

- 플레이어: 루트에 `CharacterController`(높이 1, 반지름 0.25, 중심 (0, 0.5, 0), skinWidth 0.08). 피벗이 발 위치라 캡슐은 피벗 y ~ 피벗 y + 1 구간이다. 바닥에 서 있을 때 피벗 y는 바닥 표면 + 약 0.08(skinWidth)일 것으로 추정한다([검증 필요]).
- 교훈(메모리 2026-09-17): 음식·함정 트리거가 바닥/가구 콜라이더 표면보다 낮게 깔려 있으면 캡슐과 Y축으로 겹치지 않아 충돌이 인식되지 않는다. 그 이후 사용자가 바닥 위 약 0.07~0.08에 놓는 값으로 정착했다(1-6절).
- 이번 계획의 관계식: 트리거 상단 = 스폰 Y + 로컬 상단(사과 0.186 / 치즈 0.218 / 쥐덫 0.204)이 발 위치(바닥 + 0.08)보다 커야 겹친다. 스폰 Y가 NavMesh 표면 이상이고 NavMesh 표면이 지오메트리 표면 이상이면(NavMesh는 지오메트리보다 위에 뜨는 쪽으로 오차가 나는 것이 일반적, [검증 필요]) 조건은 오프셋 0에서도 성립한다. 그래도 NavMesh 삼각형 높이의 오차 가능성과 과거 사례를 반영해 **NavMesh 지점 위로 `_spawnHeightOffset` 0.08m를 올려 배치**한다(임시, 사용자가 수동 배치한 값과 같은 크기). 오프셋을 키우면 위쪽 겹침 여유는 늘지만 플레이어 점프로 회피하는 여유(발이 트리거 상단을 넘어야 함)가 줄어 쥐덫을 넘기 어려워진다.
- 충돌 감지 여유: 물리 스텝 0.02초에 최대 10m/s(비행 중 8m/s)이면 스텝당 0.2m 이동이고 겹침 구간은 캡슐 지름 0.5 + 트리거 폭 약 0.32 = 약 0.8m라 놓치지 않는다(추정, [검증 필요]).
- `Physics.autoSyncTransforms`가 꺼져 있어(`DynamicsManager.asset` `m_AutoSyncTransforms: 0`) 트랜스폼 변경은 다음 물리 스텝 전에 반영된다. 풀에서 꺼낸 오브젝트는 위치를 옮긴 뒤에 활성화하고(4-3절 `FoodPool.Get`), 플레이어와 최소 거리(0-7)를 두므로 재생성 즉시 플레이어와 겹치는 일은 없다.

### 1-11. 이벤트 선언 현황 (0-11 근거)

`Assets/02_Scripts/`를 `delegate`, `event`로 검색한 결과다. 자동 생성 코드 `PlayerInput.cs`는 이벤트 선언이 없어 대상이 아니다.

### 4-2. `NavMeshRandomPointSampler.cs` (신규)

```csharp
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AI;

/// <summary>
/// 베이크된 NavMesh 위의 무작위 지점을 면적·높이 가중치로 뽑아 주는 클래스
/// </summary>
public class NavMeshRandomPointSampler
{
    private readonly ObjectSpawnData _spawnData;
    private readonly NavMeshQueryFilter _filter;
    private readonly Vector3[] _vertices;
    private readonly int[] _indices;
    private readonly int[] _triangleFirstIndices;
    private readonly float[] _cumulativeWeights;
    private readonly float _totalWeight;

    /// <summary>
    /// 현재 로드된 NavMesh의 삼각형을 한 번 읽어 높이 규칙을 반영한 가중치 누적 배열을 만든다. 이후 NavMesh가 바뀌어도 갱신하지 않는다
    /// </summary>
    public NavMeshRandomPointSampler(int agentTypeId, int areaMask, ObjectSpawnData spawnData)
    {
        _spawnData = spawnData;
        _filter = new NavMeshQueryFilter { agentTypeID = agentTypeId, areaMask = areaMask };

        NavMeshTriangulation triangulation = NavMesh.CalculateTriangulation();
        _vertices = triangulation.vertices;
        _indices = triangulation.indices;

        List<int> triangleFirstIndices = new List<int>();
        List<float> cumulativeWeights = new List<float>();
        float totalWeight = 0f;
        int triangleCount = _indices.Length / 3;
        for (int i = 0; i < triangleCount; i++)
        {
            if ((areaMask & (1 << triangulation.areas[i])) == 0)
            {
                continue;
            }

            Vector3 a = _vertices[_indices[i * 3]];
            Vector3 b = _vertices[_indices[i * 3 + 1]];
            Vector3 c = _vertices[_indices[i * 3 + 2]];
            float centroidY = (a.y + b.y + c.y) / 3f;
            if (IsHeightAllowed(centroidY) == false)
            {
                continue;
            }

            float area = Vector3.Cross(b - a, c - a).magnitude * 0.5f;
            if (area <= 0f)
            {
                continue;
            }

            float heightMultiplier = centroidY >= _spawnData.ElevatedHeight ? _spawnData.ElevatedWeightMultiplier : 1f;
            totalWeight += area * heightMultiplier;
            triangleFirstIndices.Add(i * 3);
            cumulativeWeights.Add(totalWeight);
        }

        _triangleFirstIndices = triangleFirstIndices.ToArray();
        _cumulativeWeights = cumulativeWeights.ToArray();
        _totalWeight = totalWeight;
    }

    /// <summary>
    /// NavMesh 전체에서 가중치에 비례해 무작위 지점을 뽑아 NavMesh 위로 스냅한다. NavMesh가 없으면 false를 반환한다
    /// </summary>
    public bool TryGetRandomPoint(out Vector3 point)
    {
        if (_totalWeight <= 0f)
        {
            point = default;
            return false;
        }

        float target = Random.value * _totalWeight;
        int index = System.Array.BinarySearch(_cumulativeWeights, target);
        if (index < 0)
        {
            index = ~index;
        }

        index = Mathf.Min(index, _cumulativeWeights.Length - 1);

        int first = _triangleFirstIndices[index];
        Vector3 a = _vertices[_indices[first]];
        Vector3 b = _vertices[_indices[first + 1]];
        Vector3 c = _vertices[_indices[first + 2]];

        float u = Random.value;
        float v = Random.value;
        if (u + v > 1f)
        {
            u = 1f - u;
            v = 1f - v;
        }

        Vector3 candidate = a + (b - a) * u + (c - a) * v;
        return SnapToNavMesh(candidate, out point);
    }

    /// <summary>
    /// 기준점을 중심으로 수평 거리 minDistance~maxDistance 링 안의 무작위 방향에서 NavMesh 위 지점을 찾는다
    /// </summary>
    public bool TryGetPointAround(Vector3 center, float minDistance, float maxDistance, out Vector3 point)
    {
        float distance = Random.Range(minDistance, maxDistance);
        float angle = Random.Range(0f, Mathf.PI * 2f);
        Vector3 candidate = center + new Vector3(Mathf.Cos(angle), 0f, Mathf.Sin(angle)) * distance;
        return SnapToNavMesh(candidate, out point);
    }

    /// <summary>
    /// 후보 지점을 가장 가까운 NavMesh 위 지점으로 옮긴다. 스냅 거리 안에 NavMesh가 없거나 제한 높이 구간이면 false를 반환한다
    /// </summary>
    private bool SnapToNavMesh(Vector3 candidate, out Vector3 point)
    {
        if (NavMesh.SamplePosition(candidate, out NavMeshHit hit, _spawnData.NavMeshSnapDistance, _filter)
            && IsHeightAllowed(hit.position.y))
        {
            point = hit.position;
            return true;
        }

        point = default;
        return false;
    }

    /// <summary>
    /// 월드 Y 높이가 생성을 제한하는 구간 밖인지 확인한다. 제한이 꺼져 있으면 항상 true다
    /// </summary>
    private bool IsHeightAllowed(float y)
    {
        if (_spawnData.RestrictHeight == false)
        {
            return true;
        }

        return y < _spawnData.RestrictedMinHeight || y > _spawnData.RestrictedMaxHeight;
    }
}
```

- 삼각형 배열과 누적 가중치는 생성자에서 한 번만 만들고 이후 호출은 이진 탐색 한 번과 `SamplePosition` 한 번이다.
- `SamplePosition` 스냅은 (1) "NavMesh 위에서만"을 쿼리 수준에서 한 번 더 보증하고, (2) 삼각형 다각형 높이 대신 NavMesh 쿼리가 돌려주는 표면 높이를 쓰고, (3) 스냅 뒤의 최종 Y가 제한 구간 밖인지 다시 확인하기 위한 것이다(1-5절 [검증 필요] 높이 차이, 0-5).
- 높이 규칙(위쪽 밀도 상승, 제한 구간)은 삼각형 가중치를 계산하는 한 곳과 `IsHeightAllowed` 한 곳에 모여 있다(6-11).

### 4-3. `FoodPool.cs` (신규)

```csharp
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.Pool;

/// <summary>
/// 음식·장애물 프리팹 하나를 재사용하는 오브젝트 풀. UnityEngine.Pool.ObjectPool을 감싼다
/// </summary>
public class FoodPool
{
    private readonly Food _prefab;
    private readonly Transform _parent;
    private readonly int _maxSize;
    private readonly ObjectPool<Food> _pool;

    /// <summary>
    /// 지금 사용 중인(풀에서 꺼내 반환하지 않은) 오브젝트 수
    /// </summary>
    public int ActiveCount => _pool.CountActive;

    /// <summary>
    /// 프리팹과 부모를 받아 풀을 만든다. 동시에 쓸 최대 수를 보관 상한으로 둔다
    /// </summary>
    public FoodPool(Food prefab, Transform parent, int maxSize)
    {
        _prefab = prefab;
        _parent = parent;
        _maxSize = maxSize;
        _pool = new ObjectPool<Food>(
            createFunc: CreateFood,
            actionOnRelease: DeactivateFood,
            actionOnDestroy: DestroyFood,
            collectionCheck: true,
            defaultCapacity: maxSize,
            maxSize: maxSize);
    }

    /// <summary>
    /// 상한만큼 비활성 인스턴스를 미리 만들어 풀에 보관한다
    /// </summary>
    public void Prewarm()
    {
        List<Food> created = new List<Food>(_maxSize);
        for (int i = 0; i < _maxSize; i++)
        {
            created.Add(_pool.Get());
        }

        for (int i = 0; i < created.Count; i++)
        {
            _pool.Release(created[i]);
        }
    }

    /// <summary>
    /// 풀에서 오브젝트를 꺼내 위치를 옮긴 뒤 활성화한다. 위치를 먼저 옮겨 재사용 순간에 이전 자리에서 트리거가 발생하지 않게 한다
    /// </summary>
    public Food Get(Vector3 position)
    {
        Food food = _pool.Get();
        food.transform.position = position;
        food.gameObject.SetActive(true);
        return food;
    }

    /// <summary>
    /// 오브젝트를 비활성화해 풀에 돌려보낸다
    /// </summary>
    public void Release(Food food)
    {
        _pool.Release(food);
    }

    /// <summary>
    /// 새 인스턴스를 부모 아래에 만들고 비활성 상태로 둔다
    /// </summary>
    private Food CreateFood()
    {
        Food food = Object.Instantiate(_prefab, _parent);
        food.gameObject.SetActive(false);
        return food;
    }

    /// <summary>
    /// 풀로 돌아온 오브젝트를 비활성화한다
    /// </summary>
    private void DeactivateFood(Food food)
    {
        food.gameObject.SetActive(false);
    }

    /// <summary>
    /// 보관 상한을 넘어 버려지는 오브젝트를 파괴한다
    /// </summary>
    private void DestroyFood(Food food)
    {
        Object.Destroy(food.gameObject);
    }
}
```

- 생성 콜백에서 바로 비활성화하고 `actionOnGet`은 넣지 않는다. 활성화는 위치를 옮긴 뒤 `Get(position)`이 수행해 순서를 보장한다(1-7절).
- 콜백 세 개는 인스턴스 메서드 그룹이라 람다가 필요 없다. `ObjectPool<T>` 생성자 인자 이름은 문서 기준이다([검증 필요], 0-10).

### 4-5. `ObjectSpawner.cs` (신규)

```csharp
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AI;

/// <summary>
/// NavMesh 위 무작위 지점에 사과·치즈·쥐덫을 오브젝트 풀로 생성·회수한다. 빈 GameObject에 부착한다
/// </summary>
public class ObjectSpawner : MonoBehaviour
{
    [SerializeField] private Player _player;
    [SerializeField] private ObjectSpawnData _spawnData;
    [SerializeField] private Food _applePrefab;
    [SerializeField] private Food _cheesePrefab;
    [SerializeField] private Food _trapPrefab;
    [SerializeField] private int _agentTypeId;
    [SerializeField] private int _areaMask = NavMesh.AllAreas;

    private readonly Dictionary<Food, FoodPool> _activeFoods = new Dictionary<Food, FoodPool>();
    private readonly List<ExpiringCheese> _expiringCheeses = new List<ExpiringCheese>();
    private NavMeshRandomPointSampler _sampler;
    private FoodPool _applePool;
    private FoodPool _cheesePool;
    private FoodPool _trapPool;
    private float _spawnTimer;

    /// <summary>
    /// 치즈와 그 만료 시각을 묶은 추적 정보
    /// </summary>
    private sealed class ExpiringCheese
    {
        /// <summary>
        /// 만료를 추적하는 치즈
        /// </summary>
        public Food Cheese;

        /// <summary>
        /// 치즈가 만료되는 Time.time 시각
        /// </summary>
        public float ExpireTime;
    }

    /// <summary>
    /// 이미 생성된 오브젝트의 소비 이벤트를 구독한다
    /// </summary>
    private void OnEnable()
    {
        foreach (Food food in _activeFoods.Keys)
        {
            food.OnConsumed += HandleFoodConsumed;
        }
    }

    /// <summary>
    /// 이미 생성된 오브젝트의 소비 이벤트 구독을 해제한다
    /// </summary>
    private void OnDisable()
    {
        foreach (Food food in _activeFoods.Keys)
        {
            food.OnConsumed -= HandleFoodConsumed;
        }
    }

    /// <summary>
    /// NavMesh 샘플러와 종류별 풀을 만들고 시작 시 일괄 생성을 시도한다
    /// </summary>
    private void Start()
    {
        _sampler = new NavMeshRandomPointSampler(_agentTypeId, _areaMask, _spawnData);

        _applePool = new FoodPool(_applePrefab, transform, _spawnData.MaxActiveApples);
        _cheesePool = new FoodPool(_cheesePrefab, transform, _spawnData.MaxActiveCheeses);
        _trapPool = new FoodPool(_trapPrefab, transform, _spawnData.MaxActiveTraps);
        _applePool.Prewarm();
        _cheesePool.Prewarm();
        _trapPool.Prewarm();

        for (int i = 0; i < _spawnData.InitialSpawnAttempts; i++)
        {
            TrySpawnRandom();
        }
    }

    /// <summary>
    /// 만료된 치즈를 회수하고 생성 주기마다 생성을 시도한다
    /// </summary>
    private void Update()
    {
        ExpireCheeses();

        _spawnTimer += Time.deltaTime;
        if (_spawnTimer < _spawnData.SpawnInterval)
        {
            return;
        }

        _spawnTimer = 0f;
        TrySpawnRandom();
    }

    /// <summary>
    /// 가중치로 사과·치즈·쥐덫 중 하나를 골라 생성을 시도한다
    /// </summary>
    private void TrySpawnRandom()
    {
        float appleWeight = _spawnData.AppleSpawnWeight;
        float cheeseWeight = _spawnData.CheeseSpawnWeight;
        float roll = Random.value * (appleWeight + cheeseWeight + _spawnData.TrapSpawnWeight);
        if (roll < appleWeight)
        {
            TrySpawnApple();
        }
        else if (roll < appleWeight + cheeseWeight)
        {
            TrySpawnCheeseWithTrap();
        }
        else
        {
            TrySpawnTrap();
        }
    }

    /// <summary>
    /// 상한을 넘지 않고 조건을 만족하는 NavMesh 위치를 찾으면 사과를 생성한다
    /// </summary>
    private void TrySpawnApple()
    {
        if (_applePool.ActiveCount >= _spawnData.MaxActiveApples)
        {
            return;
        }

        if (TryFindSpawnPosition(out Vector3 position))
        {
            SpawnFood(_applePool, position);
        }
    }

    /// <summary>
    /// 상한을 넘지 않고 조건을 만족하는 NavMesh 위치를 찾으면 치즈와 무관한 독립 쥐덫을 생성한다
    /// </summary>
    private void TrySpawnTrap()
    {
        if (_trapPool.ActiveCount >= _spawnData.MaxActiveTraps)
        {
            return;
        }

        if (TryFindSpawnPosition(out Vector3 position))
        {
            SpawnFood(_trapPool, position);
        }
    }

    /// <summary>
    /// 치즈 위치와 그 근처 동반 쥐덫 위치를 모두 찾았고 쥐덫 풀에 자리가 있을 때만 둘을 함께 생성한다
    /// </summary>
    private void TrySpawnCheeseWithTrap()
    {
        if (_cheesePool.ActiveCount >= _spawnData.MaxActiveCheeses)
        {
            return;
        }

        if (_trapPool.ActiveCount >= _spawnData.MaxActiveTraps)
        {
            return;
        }

        if (TryFindSpawnPosition(out Vector3 cheesePosition) == false)
        {
            return;
        }

        if (TryFindTrapPosition(cheesePosition, out Vector3 trapPosition) == false)
        {
            return;
        }

        ExpiringCheese expiring = new ExpiringCheese();
        expiring.Cheese = SpawnFood(_cheesePool, cheesePosition);
        expiring.ExpireTime = Time.time + _spawnData.CheeseLifetime;
        _expiringCheeses.Add(expiring);
        SpawnFood(_trapPool, trapPosition);
    }

    /// <summary>
    /// NavMesh 전체에서 최소 간격 조건을 만족하는 위치를 최대 시도 횟수만큼 찾는다
    /// </summary>
    private bool TryFindSpawnPosition(out Vector3 position)
    {
        for (int i = 0; i < _spawnData.MaxPlacementAttempts; i++)
        {
            if (_sampler.TryGetRandomPoint(out Vector3 navPoint) == false)
            {
                continue;
            }

            Vector3 candidate = ToSpawnPosition(navPoint);
            if (IsValidSpawnPosition(candidate))
            {
                position = candidate;
                return true;
            }
        }

        position = default;
        return false;
    }

    /// <summary>
    /// 치즈 주변 링 안에서 최소 간격 조건을 만족하는 쥐덫 위치를 최대 시도 횟수만큼 찾는다
    /// </summary>
    private bool TryFindTrapPosition(Vector3 cheesePosition, out Vector3 position)
    {
        float minDistance = _spawnData.TrapMinDistanceFromCheese;
        float maxDistance = _spawnData.TrapMaxDistanceFromCheese;
        for (int i = 0; i < _spawnData.MaxPlacementAttempts; i++)
        {
            if (_sampler.TryGetPointAround(cheesePosition, minDistance, maxDistance, out Vector3 navPoint) == false)
            {
                continue;
            }

            Vector3 candidate = ToSpawnPosition(navPoint);
            float sqrDistanceToCheese = (candidate - cheesePosition).sqrMagnitude;
            bool isInRing = sqrDistanceToCheese >= minDistance * minDistance
                            && sqrDistanceToCheese <= maxDistance * maxDistance;
            if (isInRing && IsValidSpawnPosition(candidate))
            {
                position = candidate;
                return true;
            }
        }

        position = default;
        return false;
    }

    /// <summary>
    /// 플레이어와 이미 생성된 모든 오브젝트로부터 최소 거리 밖인지 제곱 거리로 확인한다
    /// </summary>
    private bool IsValidSpawnPosition(Vector3 position)
    {
        float minPlayerDistance = _spawnData.MinDistanceFromPlayer;
        Vector3 toPlayer = position - _player.transform.position;
        if (toPlayer.sqrMagnitude < minPlayerDistance * minPlayerDistance)
        {
            return false;
        }

        float sqrMinObjectDistance = _spawnData.MinObjectDistance * _spawnData.MinObjectDistance;
        foreach (Food food in _activeFoods.Keys)
        {
            Vector3 offset = food.transform.position - position;
            if (offset.sqrMagnitude < sqrMinObjectDistance)
            {
                return false;
            }
        }

        return true;
    }

    /// <summary>
    /// NavMesh 표면 지점을 트리거가 플레이어 캡슐과 겹치도록 위로 띄운 배치 좌표로 바꾼다
    /// </summary>
    private Vector3 ToSpawnPosition(Vector3 navPoint)
    {
        return navPoint + Vector3.up * _spawnData.SpawnHeightOffset;
    }

    /// <summary>
    /// 풀에서 오브젝트를 꺼내 배치하고 소비 이벤트를 구독한다
    /// </summary>
    private Food SpawnFood(FoodPool pool, Vector3 position)
    {
        Food food = pool.Get(position);
        food.OnConsumed += HandleFoodConsumed;
        _activeFoods.Add(food, pool);
        return food;
    }

    /// <summary>
    /// 오브젝트의 구독을 해제하고 생성 때 꺼낸 풀로 돌려보낸다. 이미 회수된 오브젝트는 무시한다
    /// </summary>
    private void DespawnFood(Food food)
    {
        if (_activeFoods.TryGetValue(food, out FoodPool pool) == false)
        {
            return;
        }

        _activeFoods.Remove(food);
        food.OnConsumed -= HandleFoodConsumed;
        pool.Release(food);
    }

    /// <summary>
    /// 만료 시각이 지난 치즈를 회수한다. 동반 쥐덫은 치즈와 무관하게 남는다
    /// </summary>
    private void ExpireCheeses()
    {
        for (int i = _expiringCheeses.Count - 1; i >= 0; i--)
        {
            ExpiringCheese expiring = _expiringCheeses[i];
            if (Time.time >= expiring.ExpireTime)
            {
                _expiringCheeses.RemoveAt(i);
                DespawnFood(expiring.Cheese);
            }
        }
    }

    /// <summary>
    /// 소비된 치즈를 만료 추적 목록에서 뺀다
    /// </summary>
    private void RemoveExpiringCheese(Food cheese)
    {
        for (int i = 0; i < _expiringCheeses.Count; i++)
        {
            if (_expiringCheeses[i].Cheese == cheese)
            {
                _expiringCheeses.RemoveAt(i);
                return;
            }
        }
    }

    /// <summary>
    /// 플레이어에게 소비된 오브젝트를 회수한다. 치즈면 만료 추적도 함께 끝낸다
    /// </summary>
    private void HandleFoodConsumed(Food food)
    {
        RemoveExpiringCheese(food);
        DespawnFood(food);
    }
}
```

- 활성 상한은 `FoodPool.ActiveCount`(`ObjectPool.CountActive`)로 확인한다. `Food._type`을 쓰지 않으므로 프리팹의 `_type`이 잘못 설정돼도 카운트와 반환이 어긋나지 않는다(0-13, 6-3).
- 모든 위치 검증은 배치 좌표(NavMesh 표면 + 오프셋) 기준으로 통일해 오프셋 때문에 거리가 어긋나지 않게 했다. 높이 구간 확인은 NavMesh 표면 Y(오프셋 전) 기준이다(샘플러).
- 동반 쥐덫 위치를 찾을 때 치즈는 아직 `_activeFoods`에 없어 치즈와의 거리가 최소 간격 검사에 걸리지 않는다. 그래서 치즈와 쥐덫 쌍만 0-8의 별도 거리 규칙(링)을 따른다.
- 위치 탐색은 최대 시도 횟수로 끝나는 유한 루프이며, 실패하면 이번 틱은 생성하지 않고 다음 틱에 다시 시도한다(무한 루프 없음).
- 이 스포너는 `Player` 참조만 필요로 하고 `CatController`와 직접 얽히지 않는다(0-4).

### 4-6. Unity Editor 수동 작업 (코드 외 작업)

1. **`Assets/4_Prefabs/Obj/Apple_Obj.prefab`을 프리팹 편집 모드로 열어** 루트 `Apple_Obj`에 `Food` 컴포넌트를 추가한다. `_type`을 **Apple**로 바꾼다(기본값이 Obstacle이라 그대로 두면 안 된다), `_amount`는 임시 20으로 설정한다(0-13). 콜라이더는 이미 Is Trigger ON이다. 프리팹 레벨에서 작업한다(프로젝트 에셋 수준 설정은 프리팹에 둔다는 리뷰 R6의 규칙).
2. `Assets/5_Data/`에서 우클릭 -> Create -> MouseAndCheese -> Object Spawn Data로 `ObjectSpawnData.asset`을 만든다(기본값 그대로 임시로 사용). 높이 구간의 `Restrict Height`는 꺼져 있고 `Elevated Height`/`Elevated Weight Multiplier`(1, 3)만 켜져 있다. 이 값은 사용자가 씬에서 가구 위 NavMesh 높이를 확인한 뒤 정한다(0-5).
3. `SampleScene.unity`에 빈 GameObject `ObjectSpawner`를 만든다. **위치 (0,0,0), 회전 (0,0,0), 스케일 (1,1,1)**로 두고(풀 인스턴스가 이 오브젝트의 자식이 되므로 스케일이 1이 아니면 오브젝트 크기가 왜곡된다), `ObjectSpawner` 컴포넌트를 추가한 뒤 아래를 연결한다.
   - `_player`: 씬의 `Player` 오브젝트
   - `_spawnData`: 2번에서 만든 에셋
   - `_applePrefab`/`_cheesePrefab`/`_trapPrefab`: `Assets/4_Prefabs/Obj/`의 `Apple_Obj`, `Cheese_Obj`, `Trap_Obj`(**씬에 놓인 인스턴스가 아니라 프로젝트 창의 프리팹 에셋**)
   - `_agentTypeId`: 0(Humanoid), `_areaMask`: -1(모든 Area, 기본값)
4. 씬에 이미 놓인 수동 배치 `Cheese_Obj (1)`, `Cheese_Obj`, `Trap_Obj`는 풀과 무관하게 남는다. 스포너가 만든 오브젝트와 같은 `Food` 프리팹이라 인스펙터에서는 구분되지 않으므로, 테스트가 끝났다면 지울지 남길지 사용자가 결정한다(0-9). 지우지 않아도 스포너 동작에는 영향이 없다(스포너는 자신이 만든 것만 추적하고, 수동 배치 오브젝트는 최소 간격 검사 대상에도 들지 않는다).
5. `Kitchen`의 `NavMeshSurface`에 베이크 데이터가 연결돼 있는지 확인한다(`NavMesh-Kitchen.asset`). 재베이크는 필요 없다.
6. 컴파일 오류가 없는지 Console에서 확인한다. 특히 `ObjectPool<T>` 생성자 인자 이름과 `CountActive`, `NavMesh.CalculateTriangulation()`의 `areas` 배열(1-5, 0-10 [검증 필요])이 컴파일 오류로 드러날 수 있다. `Action` 전환(4-4) 뒤에는 `Player`, `CatController`, `InputManager`, `HungerController`, `Food`에서 `using System;`으로 인한 이름 모호성 오류가 없는지도 함께 본다(1-11).
7. (선택) 씬 뷰에서 Navigation 표시를 켜고 가구 위 NavMesh의 Y를 확인한 뒤 `ObjectSpawnData`의 `Elevated Height`를 조정한다. 생성을 제한할 높이 구간이 있으면 `Restrict Height`를 켜고 최소·최대를 입력한다(0-5).

## 6. 주의 사항 및 설계 결정 근거

1. **소비 통지 위치를 `IHungerObj`/`HungerController`가 아닌 `Food`로 잡은 이유(리뷰 R5와 다른 점)**: R5는 `HungerController.OnTriggerEnter`가 `IHungerObj.Consume()`을 호출하는 방식을 제안했으나, 현재 트리거 처리는 `Food.OnTriggerEnter`가 직접 한다(1-1). 소비가 실제로 일어나는 곳(`ChangeHunger` 호출 직후)이 `Food`이므로 거기서 통지하는 것이 가장 작은 변경이다. 소비 통지를 위해서는 `HungerController.cs`와 `IHungerObj.cs`를 건드리지 않는다(`HungerController.cs`는 `Action` 전환 때문에만 수정한다, 6-13).
2. **이벤트(`OnConsumed`)로 통지하고 `Food`가 풀을 모르게 한 이유**: `Food`가 풀 참조를 들고 `pool.Release(this)`를 호출하는 방식(엔진 문서의 흔한 패턴)은 `Food`가 스폰 시스템에 의존하게 만든다. 이벤트로 통지하면 `Food`는 "소비됐다"만 말하고, 수동 배치 오브젝트처럼 구독자가 없는 `Food`도 지금 그대로 동작한다. 점수·랭킹 Feature도 같은 이벤트를 구독해 종류를 읽을 수 있다. 구독은 `SpawnFood`/`DespawnFood` 쌍과 `OnEnable`/`OnDisable` 루프로 대칭을 지켰다.
3. **반환 대상을 `Food._type`이 아니라 `_activeFoods[food]`(생성 때 꺼낸 풀)로 정한 이유**: `Food._type`의 기본값이 첫 열거값 `Obstacle`이라, `Apple_Obj`에 `Food`를 새로 붙이고 `_type`을 바꾸지 않으면 사과가 쥐덫 풀로 반환돼 풀이 뒤섞인다. 어느 풀에서 나왔는지를 기록해 두면 프리팹의 `_type` 설정 실수와 무관하게 안전하고, 이중 반환도 `TryGetValue` 실패로 자연스럽게 걸러진다. 활성 상한도 `ObjectPool.CountActive`로 확인해 종류 정보에 의존하지 않는다.
4. **`FoodPool`, `NavMeshRandomPointSampler`를 일반 C# 클래스로 만든 이유**: 둘은 씬에 붙일 대상이 아니라 스포너가 소유하는 도구이고 인스펙터 연결이 필요 없다(`Start`에서 스포너가 생성). MonoBehaviour로 만들면 빈 GameObject와 참조 연결만 늘어난다. 프로젝트에 일반 C# 클래스 선례가 없다는 점은 새로운 시도이나, DI/싱글톤을 도입하지 않고 소유 관계로 해결한 것이다. `FoodPool`이 프리팹당 하나로 `ObjectPool<Food>`를 감싼 것은 콜백(`CreateFood` 등)이 인스턴스 메서드 그룹이 되어 프리팹별 캡처용 람다가 필요 없어지기 때문이다.
5. **랜덤 지점을 NavMesh 삼각형 가중치로 뽑는 이유(1-10 비교)**: 방식 B(바운딩 박스 + `SamplePosition`)는 가구 구멍 주변에서 가장자리에 몰리거나 기각이 잦고 한 높이만 찾아 가구 위가 누락된다. 삼각형 추출은 높이와 구멍을 자동으로 처리하고, 삼각형별 가중치를 곱하는 한 곳에서 사용자가 정한 높이 규칙(0-5)을 표현할 수 있다. 이후 `SamplePosition`으로 스냅해 "NavMesh 위"를 쿼리 수준에서 한 번 더 확인한다. 한계: (a) 시작 시 1회 캐시라 런타임 재베이크에는 낡는다(현재 런타임 재베이크 없음), (b) `CalculateTriangulation()`은 에이전트 타입 구분 없이 로드된 전체를 돌려주는데 이 프로젝트는 타입이 Humanoid 하나뿐이다, (c) 삼각형 높이와 `SamplePosition` 높이의 차이는 검증하지 못했다([검증 필요]). 캐시는 `Start`에서 만든다. `NavMeshSurface`의 데이터는 `OnEnable` 시점에 등록되고 모든 `Start`는 그 뒤에 실행되므로 순서상 안전하다고 본다([검증 필요]).
6. **Y 좌표(오프셋)와 트리거 상하 범위**: 1-7절의 관계식과 사용자가 수동 배치에서 쓴 0.066~0.08 값을 근거로 임시 오프셋 0.08을 뒀다. 이 값이 크면 쥐덫을 넘기 어렵고(트리거 상단이 높아짐), 작으면 NavMesh 삼각형 높이 오차에 취약하다. 시나리오 13·14에서 확인하고 조정한다.
7. **전체 맵 유지 개수 방식을 택한 이유**: 맵이 닫힌 방이고 전진 방향이 카메라 상대라 "플레이어 앞쪽 범위" 기준이 성립하기 어렵다(0-4). 사용자가 확정한 "시작 시 일괄 + 이후 지속 생성 + 플레이어와의 거리만 확인"을 종류별 상한 + 타이머 보충으로 구현했다. 상한은 "밀도 상한"을 자연스럽게 표현해 GDD가 경계한 "특정 구간에 몰려 불공평하게 배치"를 최소 간격과 함께 완화한다. 다만 방 전체에서 가중치로 추출해 우연히 한 곳에 몰리는 것을 완전히 막지는 못한다. 셀 단위 상한이나 푸아송 디스크 샘플링은 사용자 결정 이후의 후보다.
8. **위치 탐색은 유한 시도 후 포기**: 조건을 만족하는 위치를 못 찾으면 그 틱은 생성하지 않는다. 상한이 크거나 간격이 넓어 자리가 없을 때 무한 루프나 프레임 스파이크가 생기지 않는다. 대신 상한만큼 채워지지 않는 상태가 오래 지속될 수 있어 시나리오 12에서 관찰한다.
9. **풀을 `Clear()`하지 않는 이유**: 풀 인스턴스가 스포너의 자식이라 씬이 내려갈 때 함께 파괴된다. `OnDestroy`에서 `ObjectPool.Clear()`를 호출하면 이미 파괴된 자식에 접근해 예외가 날 수 있어 넣지 않았다(리스타트 Feature가 생기면 그 시점에 정리한다). 상한을 넘겨 반환된 인스턴스는 파괴 콜백(`DestroyFood`)이 처리한다. 현재 상한이 풀 크기와 같아 실제로 파괴되는 경우는 없다.
10. **치즈 만료를 `ExpiringCheese`로 따로 추적하는 이유**: 쥐덫이 치즈와 무관하게 생성·존속하므로(0-8) 치즈와 쥐덫을 묶는 자료구조는 필요 없다. 만료가 있는 것은 치즈뿐이라 "치즈와 만료 시각"만 담는 작은 클래스를 목록으로 관리한다(치즈 상한 2, 할당은 무시할 수준). 이전 버전의 `CheeseGroup`(치즈+쥐덫+만료)은 쥐덫 수명 연동을 전제한 것이라 없앴다.
11. **높이 구간 규칙의 위치와 한계**: 사용자가 높이 구간으로 정하기로 했으므로(0-5) 규칙을 샘플러 두 곳에 모았다. (a) 삼각형 가중치 계산에서 무게 중심 Y로 "제외/배율/그대로"를 정하고, (b) `SnapToNavMesh`가 스냅한 최종 Y를 `IsHeightAllowed`로 다시 확인한다. 사과·치즈·쥐덫이 한 샘플러를 공유하므로 규칙이 세 종류에 똑같이 적용된다. 한계는 무게 중심 근사와 배율이 낮을 때 체감이 작다는 점(0-5 위험)이고, 종류별로 다른 규칙이 필요하면 샘플러를 종류별로 나눈다. 제한 구간은 값이 정해지기 전에 생성을 막지 않도록 기본으로 꺼 두었다(`_restrictHeight` false).
12. **쥐덫 독립 생성의 결과와 치즈 굶주림 위험**: 쥐덫이 치즈와 무관하게 남으므로 수명이 없는 쥐덫이 밟히기 전까지 풀 상한(6)을 차지한다. 치즈는 동반 쥐덫 자리가 있어야 생성되므로(GDD "치즈는 항상 쥐덫과 함께"), 쥐덫이 상한까지 차면 치즈가 생성되지 않는 상태가 될 수 있다. 사용자가 쥐덫 수명·상한 정책을 정하지 않았으므로 코드로 막지 않고 0-8에 후보를 적었으며 시나리오 20으로 관찰한다.
13. **`Action` 전환의 범위와 안전성**: 사용자 지시로 새 이벤트와 기존 이벤트 전부를 `Action`으로 통일한다(0-11, 1-11). 커스텀 델리게이트와 `Action`은 `+=`/`-=`/`?.Invoke` 사용법과 성능이 같고, 구독 코드가 메서드 그룹이라 핸들러 시그니처가 같으면 코드 변경이 없다. 델리게이트 타입 이름을 다른 파일이 참조하지 않아 선언 삭제로 깨지는 곳이 없다. `using System;`은 `Random`/`Object` 사용 파일에서 `System`의 같은 이름과 충돌하므로 스폰 파일에는 넣지 않고 전환 대상 5개 파일에만 넣는다(그 파일들에는 두 이름의 사용이 없다). 이전 계획서(26_0919, 26_0920)와 리뷰에 남은 "이벤트는 커스텀 델리게이트만 쓴다" 서술은 이력 문서라 고치지 않는다.
14. **씬의 기존 수동 배치 오브젝트는 이번 계획에서 제거하지 않는다**: 사용자가 테스트용으로 놓은 것이므로 지울지는 사용자가 정한다(4-6절 4번). 스포너는 자신이 만든 오브젝트만 추적하므로 남아 있어도 최소 간격 검사 대상이 되지 않는다. 같은 자리에 스폰돼 겹칠 수 있다는 점만 유의한다.
15. **고양이·경로 기록과의 무관성**: 음식·쥐덫은 `NavMeshObstacle`이 아니고 트리거라 고양이 이동을 막지 않는다. `PlayerPathRecorder`와 `CatController`는 음식 위치를 참조하지 않는다. 풀잎 비행 중 플레이어가 음식 근처를 지나면 지상과 같이 소비된다.
16. **밀도와 밸런스는 검증되지 않았다**: 0-6의 추정(무작위 주행 시 사과 약 15초에 1개)이 맞다면 임시 상한 20도 배고픔 감소(만복에서 약 25초)에 비해 낮을 수 있다. 실제로는 플레이어가 보이는 사과를 향해 조향하므로 체감은 다르다. 쥐덫 독립 생성(가중치 2, 상한 6)이 이동 경로에 주는 부담도 미검증이다. 수치 확정은 사용자가 플레이하며 밸런스를 보고 정한다(0-6, 0-7, 0-13).

19. **코딩 컨벤션 준수**: 모든 필드·메서드에 접근 제어자 명시(중첩 클래스 `ExpiringCheese`는 `private sealed`, 그 필드는 public이라 summary 작성), `var` 미사용(타입 항상 명시), `!` 대신 `== false` 사용(`TryFindSpawnPosition(...) == false`, `_sampler.TryGetRandomPoint(...) == false`, `IsHeightAllowed(...) == false` 등), 클래스·메서드·public 멤버에 한국어 `/// <summary>`(핵심 한 줄, 설계 근거는 본문에만), 람다식 미사용(콜백은 메서드 그룹), 이벤트는 사용자 지시에 따라 `System.Action`으로 선언(0-11). `_player`, `_spawnData`, 프리팹 세 개는 필수 참조라 미연결 시 예외가 나는 fail-fast를 유지했고 디버깅용 null 체크를 넣지 않았다. `Food.cs`는 기존 스타일(`if(`, 공백 없음)을 유지해 변경 줄만 diff에 나오게 했다.
