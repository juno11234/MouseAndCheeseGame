# 배고픔 속도 시스템 (System: 배고픔·속도 스탯 / Feature: 배고픔 속도 시스템) 구현 계획

- 작성 날짜: 2026-09-15 (26_0915)
- 작성자: planner (Claude Code)
- 요청 범위: Notion에 이미 정의된 아래 4개 Task를 구현한다.
  1. 장애물 충돌 시 게이지가 감소된다
  2. 음식 충돌 시 게이지가 회복된다
  3. 배고픔 게이지에 따라 속도 조절
  4. 배고픔 0 도달 시 즉사 대신 최저 속도로 전환 (고양이에게 잡히면 그때 게임오버 — 게임오버 판정 자체는 이번 범위 밖)
- 배경(기획 의도, 재조사 불필요): 배고픔 게이지 = 이동 속도. 시간 경과 지속 감소, 사과는 소량 회복, 치즈는 즉시 풀 회복, 장애물 충돌은 추가 감소, 배고픔↔이동속도는 매핑 곡선으로 변환.
- 인접 Feature와의 경계(이번 계획에서 직접 구현하지 않음, 아래 6절 참고):
  - "데이터 테이블" System의 "플레이어,고양이 스탯 관련 데이터 테이블" Feature → 배고픔 감소 속도, 최저/최고 이동 속도 등 플레이어 자체 스탯 값을 소유. 이번 계획은 ScriptableObject 참조 구조만 만들고 필요한 최소 필드만 임시로 가정한다. (장애물 페널티/음식 회복량은 IHungerObj 도입에 따라 각 오브젝트 쪽 데이터로 이동했으므로 이 테이블 소관이 아니다 — 6-5절 근거)
  - "속도 연출"(카메라 FOV/블러), "배고픔 UI" Feature → 이번 계획은 그들이 구독/폴링할 수 있는 공개 프로퍼티·이벤트만 제공한다.
  - "고양이 AI"의 "플레이어 추격" Feature → 배고픔 비율을 읽어 갭을 계산하고 게임오버를 판정하는 것은 그쪽 책임. 이번 계획은 값 제공과 "0 도달 시 최저 속도 전환"까지만 담당한다.
  - "음식·장애물 랜덤 생성"(오브젝트별 소환 로직) Feature → 사과/치즈/쥐덫/장애물 프리팹을 실제로 만드는 쪽. 이번 계획이 정의하는 `IHungerObj` 인터페이스를 그 프리팹들이 구현해야 한다는 계약을 남긴다(6-5절 근거).

## 1. 코드베이스 조사 결과

### 1-1. 관련 기존 스크립트
- `Assets/02_Scripts/Player.cs`: `[RequireComponent(typeof(CharacterController))]`. `InputManager`/`CameraController`를 `[SerializeField]`로 참조받아 조합(composition)하는 구조. `Update()`에서 `ApplyGravity()` → `HandleMovement()` → `HandleRotation()` 순서로 호출. 현재 수평 이동 속도는 `[SerializeField] private float _moveSpeed = 5f;` 고정값을 `HandleMovement()`에서 그대로 사용 중(`_characterController.Move(moveDirection * (_moveSpeed * Time.deltaTime))`). 이 고정값을 배고픔 기반 동적 속도로 교체하는 것이 이번 계획의 핵심 변경점이다.
- `Assets/02_Scripts/Input/InputManager.cs`: 커스텀 델리게이트(`public delegate void InputButtonHandler(bool isPressed);`)로 이벤트를 선언하는 패턴, `OnEnable`/`OnDisable`에서 대칭적으로 구독/해제하는 패턴을 확인.
- `Assets/02_Scripts/CameraController.cs`: `ForwardDirection` 프로퍼티를 캐싱하지 않고 매 호출마다 즉시 계산하는 패턴을 확인. 주석에 "Update 실행 순서에 따른 한 프레임 지연 문제를 피하기 위함"이라고 명시되어 있음 — 이번 계획의 `CurrentMoveSpeed` 설계에 동일 패턴을 재사용한다(6-2절 근거).
- DI 프레임워크/Singleton/ServiceLocator 없음. 모든 참조는 `[SerializeField]`로 인스펙터에서 직접 연결하는 방식(기존 관례를 그대로 따른다).
- 인터페이스(`interface`)를 사용한 코드는 프로젝트 전체에 없었으나, 이번 수정(주석 반영)으로 `IHungerObj`가 프로젝트 최초의 인터페이스가 된다(6-5절 근거). 열거형(`enum`)도 이번에 `HungerObjType`이 최초로 추가된다.

### 4-1. `IHungerObj.cs` (신규)

```csharp
/// <summary>
/// IHungerObj를 구현하는 오브젝트의 종류. 장애물/음식(사과/치즈)을 구분한다.
/// </summary>
public enum HungerObjType
{
    Obstacle,
    Apple,
    Cheese
}

/// <summary>
/// 배고픔 변경을 유발하는 오브젝트(음식/장애물)가 구현하는 인터페이스.
/// 음식·장애물 프리팹은 이 인터페이스를 구현한 컴포넌트를 부착해 HungerController와 소통한다.
/// </summary>
public interface IHungerObj
{
    /// <summary>
    /// 이 오브젝트의 종류(장애물/사과/치즈). 배고픔 변경 계산에는 쓰이지 않지만, 종류 구분이 필요한
    /// 다른 Feature(예: 점수 시스템)가 GetComponent로 이 인터페이스를 얻어 읽을 수 있다
    /// (6-12절 근거 — 이전에는 종류를 알 방법이 없었던 문제를 이 프로퍼티가 부분적으로 해소한다)
    /// </summary>
    HungerObjType HungerObjType { get; }

    /// <summary>
    /// 이 오브젝트와 접촉했을 때 배고픔에 적용할 변경량을 그대로 들고 있는다.
    /// 장애물은 음수, 음식은 양수를 값 자체에 이미 반영해 저장한다(별도 가공 함수 없음).
    /// 치즈의 "즉시 풀 회복"은 이 값을 MaxHunger보다 충분히 큰 양수로 구성해두면, HungerController의
    /// clamp가 자연스럽게 풀 회복으로 만들어준다(6-4절 근거).
    /// </summary>
    float Amount { get; }
}
```

### 4-2. `PlayerStatData.cs` (신규, 임시 스텁)

```csharp
using UnityEngine;

/// <summary>
/// 플레이어의 배고픔·이동속도 밸런싱 수치를 담는 데이터 테이블 스크립터블 오브젝트.
/// "플레이어,고양이 스탯 관련 데이터 테이블" Feature에서 정식으로 구현될 예정이며,
/// 이 클래스는 그 전까지 HungerController가 참조할 최소한의 필드 계약(임시 스텁)이다.
/// 실제 밸런싱 값이 담긴 정식 에셋 제작은 이번 Feature 범위 밖이다.
/// </summary>
[CreateAssetMenu(fileName = "PlayerStatData", menuName = "MouseAndCheese/Player Stat Data")]
public class PlayerStatData : ScriptableObject
{
    [Header("배고픔")]
    [SerializeField] private float _maxHunger = 100f;
    [SerializeField] private float _hungerDecayPerSecond = 2f;

    [Header("배고픔 -> 이동속도 매핑")]
    [SerializeField] private float _minMoveSpeed = 2f;
    [SerializeField] private float _maxMoveSpeed = 8f;
    [SerializeField] private AnimationCurve _hungerToSpeedCurve = AnimationCurve.Linear(0f, 0f, 1f, 1f);

    /// <summary>
    /// 배고픔 게이지의 최대치
    /// </summary>
    public float MaxHunger => _maxHunger;

    /// <summary>
    /// 초당 배고픔 감소량
    /// </summary>
    public float HungerDecayPerSecond => _hungerDecayPerSecond;

    /// <summary>
    /// 배고픔 비율(0~1)을 이동 속도로 변환한다. _hungerToSpeedCurve로 곡선 형태(가속/감속 구간)를 조정하고,
    /// 곡선 평가 결과(0~1)를 _minMoveSpeed~_maxMoveSpeed 구간에 선형 보간해 최종 이동 속도를 계산한다
    /// </summary>
    public float EvaluateMoveSpeed(float hungerRatio)
    {
        float curveValue = _hungerToSpeedCurve.Evaluate(Mathf.Clamp01(hungerRatio));
        return Mathf.Lerp(_minMoveSpeed, _maxMoveSpeed, Mathf.Clamp01(curveValue));
    }
}
```

### 4-3. `HungerController.cs` (신규)

```csharp
using UnityEngine;

/// <summary>
/// 플레이어의 배고픔 게이지를 관리하고, 배고픔 수치를 이동 속도로 매핑하여 Player에게 제공하는 클래스.
/// 시간 경과에 따른 지속 감소와 `IHungerObj`를 구현한 트리거 콜라이더(장애물/음식)와의 접촉을
/// 하나의 `ChangeHunger` 경로로 통합 처리하며, 배고픔이 변경될 때마다 통합 이벤트로 외부(연출, UI, 고양이 AI 등)에 알린다.
/// 이 스크립트는 트리거 이벤트를 받을 수 있는 Collider(CharacterController 포함)가 부착된
/// Player GameObject에 함께 부착한다.
/// </summary>
public class HungerController : MonoBehaviour
{
    public delegate void HungerChangedHandler(float hungerRatio);

    [SerializeField] private PlayerStatData _playerStatData;

    private float _currentHunger;

    /// <summary>
    /// 배고픔 수치가 변경될 때마다 발생하는 통합 이벤트 (현재 배고픔 비율 0~1 전달).
    /// 시간 경과 감소, 장애물 충돌, 음식 섭취 등 배고픔이 바뀌는 모든 경로가 이 이벤트 하나로 알림을 보낸다
    /// </summary>
    public event HungerChangedHandler OnHungerChanged;

    /// <summary>
    /// 현재 배고픔 수치 (0 ~ PlayerStatData.MaxHunger)
    /// </summary>
    public float CurrentHunger => _currentHunger;

    /// <summary>
    /// 현재 배고픔 비율 (0~1). UI/연출/고양이 AI 등 다른 Feature가 배고픔 상태를 읽는 공개 인터페이스
    /// </summary>
    public float HungerRatio => Mathf.Clamp01(_currentHunger / _playerStatData.MaxHunger);

    /// <summary>
    /// 현재 배고픔 비율을 데이터 테이블의 매핑 곡선으로 변환한 이동 속도.
    /// 값을 캐싱하지 않고 매 호출마다 최신 배고픔 수치로 즉시 계산한다
    /// (CameraController.ForwardDirection과 동일하게, Update 실행 순서에 따른 한 프레임 지연을 피하기 위함)
    /// </summary>
    public float CurrentMoveSpeed => _playerStatData.EvaluateMoveSpeed(HungerRatio);

    /// <summary>
    /// 배고픔 수치를 최대치로 초기화한다
    /// </summary>
    private void Awake()
    {
        _currentHunger = _playerStatData.MaxHunger;
    }

    /// <summary>
    /// 매 프레임 시간 경과에 따라 배고픔을 지속 감소시킨다
    /// </summary>
    private void Update()
    {
        ChangeHunger(-_playerStatData.HungerDecayPerSecond * Time.deltaTime);
    }

    /// <summary>
    /// IHungerObj를 구현한 트리거 콜라이더(장애물/음식)와 접촉하면, 그 오브젝트가 들고 있는
    /// Amount(부호까지 반영된 변경량)를 그대로 가져와 배고픔에 적용한다.
    /// 장애물인지 음식인지는 이 클래스가 직접 분기하지 않는다 — 각 오브젝트가 자신의 Amount 값 자체로 표현한다
    /// </summary>
    private void OnTriggerEnter(Collider other)
    {
        if (other.TryGetComponent(out IHungerObj hungerObj))
        {
            ChangeHunger(hungerObj.Amount);
        }
    }

    /// <summary>
    /// 배고픔 수치를 변경량(amount)만큼 증감시키고 0~MaxHunger로 clamp한 뒤 OnHungerChanged 이벤트를 발생시킨다.
    /// 시간 경과 감소, 장애물 충돌, 음식 섭취 등 배고픔을 바꾸는 모든 경로가 이 메서드 하나를 거친다.
    /// 0에 도달해도 별도의 즉사 처리는 하지 않는다 — CurrentMoveSpeed가 최저 속도로 자연스럽게 수렴할 뿐이며,
    /// 그 상태에서의 게임오버 판정은 고양이 AI("플레이어 추격") Feature의 책임이다
    /// </summary>
    public void ChangeHunger(float amount)
    {
        _currentHunger = Mathf.Clamp(_currentHunger + amount, 0f, _playerStatData.MaxHunger);
        OnHungerChanged?.Invoke(HungerRatio);
    }
}
```

/// 계산한 값을 그대로 사용한다 (배고픔이 낮을수록 느려지고, 0이어도 최저 속도로 계속 이동한다)

## 6. 주의 사항 및 설계 결정 근거

1. **장애물도 물리적으로 막지 않고 트리거로 통일 처리**: 장애물을 단단한 콜라이더(Solid)로 만들면 `OnControllerColliderHit`을 써야 하는데, 이는 접촉이 지속되는 동안 매 프레임 반복 호출되어 정지 상태로 눌리면 배고픔이 순식간에 0으로 급감하는 문제가 생긴다(별도 쿨다운 로직이 필요해짐). 반면 `OnTriggerEnter`는 Unity가 한 번 진입할 때 한 번만 호출하므로 추가 디바운스 로직 없이 "충돌 1회 = 페널티 1회"가 자연스럽게 보장된다. 또한 배고픔이 0이어도 즉사하지 않고 계속 달리게 한다는 기획 의도(멈추지 않는 러너)와도 장애물을 통과 가능한 트리거 존으로 설계하는 편이 자연스럽게 맞는다. 장애물을 물리적으로 막아야 한다는 요구사항은 Task 목록에 없으므로 임의로 추가하지 않았다.
2. **`CurrentMoveSpeed`를 캐싱 필드가 아닌 계산된 프로퍼티로 설계**: `HungerController.Update()`(배고픔 감소)와 `Player.Update()`(이동 적용) 중 어느 쪽이 먼저 실행될지는 Unity의 기본 스크립트 실행 순서로는 보장되지 않는다. 값을 필드에 캐싱하면 순서에 따라 한 프레임 지연된 속도가 적용될 수 있으므로, `CameraController.ForwardDirection`과 동일하게 매 호출마다 최신 `_currentHunger` 기준으로 즉시 계산하는 프로퍼티로 만들어 이 문제를 원천 차단했다(1-1절에서 확인한 기존 패턴을 그대로 재사용).
3. **`PlayerStatData`는 임시 스텁임을 명시**: 사용자 요청에 따라 실제 데이터 테이블 에셋 제작은 범위 밖이지만, `HungerController`가 하드코딩 없이 동작하려면 최소한의 참조 대상 타입이 있어야 하므로 이번 계획에 포함했다. "플레이어,고양이 스탯 관련 데이터 테이블" Feature가 실제로 구현될 때 필드명/클래스 구조가 달라질 수 있으며, 그 시점에 `HungerController`의 참조 타입도 함께 갱신이 필요할 수 있음을 인지하고 있어야 한다.
4. **치즈의 "즉시 풀 회복"은 코드 분기 없이 데이터 쪽 값으로 표현한다**: `HungerController`는 특정 종류를 코드로 분기하지 않는다. 대신 치즈 프리팹의 `Amount`를 `MaxHunger`보다 충분히 큰 양수로 설정해두면, `ChangeHunger`의 `Clamp`가 자연스럽게 풀 회복을 만들어낸다. 이 값을 얼마로 둘지는 치즈 프리팹을 만드는 "음식·장애물 랜덤 생성" Feature의 책임이다.
5. **인터페이스 기반 식별로 전환 (태그 대신)**: 사용자 주석 요청에 따라, 애초 계획했던 `CompareTag("Obstacle"/"Apple"/"Cheese")` 3분기 방식을 폐기하고 `IHungerObj` 인터페이스로 통일했다. `HungerController.OnTriggerEnter`는 이제 `TryGetComponent<IHungerObj>` 하나로 장애물/사과/치즈를 구분 없이 처리하며, `Amount`가 이미 담고 있는 부호와 크기만으로 모든 분기를 대체한다. 이에 따라 Tag Manager에 태그를 신규 추가할 필요가 없어졌다(1-3절). 다만 이 인터페이스가 "음식·장애물 랜덤 생성" Feature가 만들 모든 프리팹과 새로 공유하는 계약이 된다는 점은 이전 태그 계약과 동일하게 유효하다 — 그 Feature 구현 시 반드시 `IHungerObj`를 구현해야 한다(4-5절 4번 항목에 명시).
6. **오브젝트 종류를 `HungerObjType` 열거형으로 표현, 별도 파일 대신 `IHungerObj.cs`에 함께 선언**: 사용자 주석 요청에 따라 이전 계획의 `FoodType.cs`(사과/치즈만 구분)를 폐기하고, 장애물까지 포괄하는 `HungerObjType`(Obstacle/Apple/Cheese) 열거형을 `IHungerObj.cs` 파일 상단에 함께 선언했다. 열거형을 인터페이스와 같은 파일에 두라는 지시를 그대로 따랐다.
7. **오브젝트가 최종 변경량(`Amount`)을 그대로 보유, 별도 계산 함수는 두지 않음**: 사용자 주석 반영 과정에서 한 차례 `GetChangeAmount(float, HungerObjType)`라는 계산 메서드를 추가했었으나, "변경량 자체를 오브젝트가 들고 있으면 되고 별도 함수는 필요 없다"는 정정에 따라 제거했다. `Amount`는 이미 부호까지 반영된 최종값(장애물은 음수, 음식은 양수)이며, `HungerController`는 이 값을 그대로 `ChangeHunger`에 전달하기만 한다. 구현체(장애물/사과/치즈 프리팹)는 자신의 `Amount`를 원하는 부호/크기로 직접 설정하면 된다.
8. **이벤트를 하나로 통합**: 애초 계획에서는 `OnHungerChanged`/`OnObstacleHit`/`OnFoodEaten` 3개의 이벤트로 나눴으나, 사용자 주석 요청에 따라 `OnHungerChanged` 하나로 통합했다. 배고픔 변화를 구독하는 대부분의 인접 Feature(속도 연출, UI)는 "무엇 때문에 바뀌었는지"보다 "현재 비율이 얼마인지"만 필요하므로 통합에 따른 정보 손실이 실질적으로 없다. 커스텀 델리게이트(`HungerChangedHandler`) 선언 방식은 `InputManager.cs`의 기존 관례를 그대로 따랐으며, 람다식은 사용하지 않았다.
9. **`Awake()`에서 `_playerStatData` null 체크를 하지 않음**: CLAUDE.md 규칙("디버깅 로그를 띄우기 위해 null 체크를 하지 않는다")과 기존 코드 스타일(`CameraController`도 `_cameraTransform`/`player` 등 필수 참조에 null 체크 없이 직접 접근) 모두를 따라, `_playerStatData`가 인스펙터에 연결되지 않으면 `NullReferenceException`이 그대로 발생하도록 두었다(fail-fast). 이는 "연결을 잊었다"는 사실을 즉시 드러내는 의도된 동작이다.
10. **고양이 AI/게임오버 로직을 포함하지 않음**: 배경에 명시된 대로 "배고픔이 0에 도달해도 즉사하지 않는다"는 요구사항은 `ChangeHunger`가 값을 0으로 clamp하고 `CurrentMoveSpeed`가 `PlayerStatData`의 최소 이동속도로 자연스럽게 수렴하는 것만으로 충족되며, 별도의 "즉사 분기"를 만들지 않았다. 갭 계산/게임오버 판정은 "고양이 AI"의 "플레이어 추격" Feature가 `HungerRatio`를 읽어 처리할 몫이므로 이번 계획에 포함하지 않았다. 다만 최소 이동속도가 0보다 커야 "즉사하지 않는다"는 요구사항이 실제로 지켜지므로, `PlayerStatData._minMoveSpeed`를 0보다 큰 값으로 설정하는 것은 데이터 테이블(밸런싱) 쪽의 책임으로 남긴다.
11. **점프/중력은 배고픔의 영향을 받지 않도록 범위 한정**: Task 목록의 "속도 조절"은 전진 이동 속도에 한정된다고 해석했다. `Player.HandleMovement()`에서만 `_hungerController.CurrentMoveSpeed`를 사용하고, `ApplyGravity()`/`HandleJumpInput()`의 `_jumpForce`, 중력 값은 그대로 두어 요구되지 않은 범위까지 임의로 확장하지 않았다.
12. **점수 시스템이 필요로 하는 음식 종류 구분은 이번 변경으로 부분적으로 해소됨**: 이전 버전(수정 01)에서는 `HungerController`가 사과/치즈를 전혀 구분하지 않아 "점수·랭킹 시스템"이 종류를 알아낼 방법이 없다는 점을 미해결로 남겼었다. `HungerObjType` 도입으로, 음식 오브젝트에 붙은 `IHungerObj` 컴포넌트를 `GetComponent`로 얻으면 어떤 종류인지 다른 Feature도 직접 읽을 수 있게 되어 이 문제가 부분적으로 해소됐다. 다만 `HungerController.OnHungerChanged` 이벤트 자체에는 여전히 종류 정보가 실리지 않으므로, 점수 시스템이 그 이벤트만 구독해서 종류를 구분하는 것은 불가능하다 — 자체적으로 트리거를 감지하거나 `IHungerObj`를 직접 조회해야 한다. 이 접근 방식 자체를 채택할지는 "점수·랭킹 시스템" Feature 계획 시점에 확정해야 한다.
13. **코딩 컨벤션 준수**: 모든 필드/메서드에 접근 제어자 명시, `var` 미사용, `!` 대신 `== null`/조건식 사용(단일 bool 부정 케이스 없음), 클래스·public 멤버에 한국어 `<summary>` XML 주석 작성, 람다식 미사용. `Player.cs`는 사용자가 직접 관리해 온 파일이므로 실제 수정 전 사용자 확인이 필요하다(CLAUDE.md 파일 수정 규칙, 3절 하단 참고).

## 수정 이력

- 수정 01: 음식/장애물을 `IHungerObj` 인터페이스로 묶고 `ChangeHunger` 함수에 변경량을 인자로 전달하는 방식으로 통일, 이벤트도 `OnHungerChanged` 하나로 통합 — `FoodType.cs`와 태그 기반 `CompareTag` 3분기(`HandleObstacleHit`/`HandleFoodEaten`/`SetHunger`)를 제거하고 `IHungerObj.cs`를 신규로 추가했다. `PlayerStatData`에서 `ObstaclePenalty`/`AppleRecoverAmount` 필드를 제거했으며(변경량이 각 오브젝트 쪽 데이터로 이동), Tag Manager에 태그를 추가할 필요가 없어졌다. 이 과정에서 드러난 부수 효과(점수 시스템의 음식 종류 구분 필요성)는 6-12절에 결정 보류 사항으로 남겼다.
- 수정 02: `HungerObjType` 열거형을 추가해 음식/장애물 종류를 구분하고, 열거형은 별도 파일 대신 `IHungerObj.cs`에 함께 선언. 인터페이스는 최종 변경량(부호까지 반영된 값)을 그대로 보유하는 `Amount` 프로퍼티와 `HungerObjType` 프로퍼티 두 개만 노출하며, 별도의 계산 함수는 두지 않는다(중간에 `GetChangeAmount(float, HungerObjType)` 메서드를 추가했다가, "인자값과 반환값을 혼동했다"는 사용자 정정에 따라 제거하고 이 형태로 확정). `HungerController.OnTriggerEnter`는 `hungerObj.Amount`를 그대로 `ChangeHunger`에 전달한다. 이 변경으로 6-12절의 미해결 사항(점수 시스템의 음식 종류 구분)이 `HungerObjType` 프로퍼티를 통해 부분적으로 해소됨을 반영했다.
