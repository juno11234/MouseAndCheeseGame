# 데이터 테이블 (System: 데이터 테이블 / Feature: "플레이어,고양이 스탯 관련 데이터 테이블" + "음식 장애물 생성 관련 데이터 테이블" + "점수 집계 관련 데이터 테이블") 구현 계획

- 작성 날짜: 2026-09-24 (26_0924)
- 작성자: planner (Claude Code)
- 요청 범위: 사용자가 게임 밸런스·기획 수치를 Unity Inspector 대신 Google 스프레드시트("MouseAndCheeseTable")에서 관리하고, 게임에서 쓸 수 있는 데이터 테이블로 만들고 싶어한다. 대상은 이미 프로젝트에 6개 존재하는 임시 스텁 ScriptableObject(`PlayerStatData`, `CatStatData`, `LeafFlightData`, `ObjectSpawnData`, `SpeedEffectData`, `ScoreData`)들이 각자 "정식 수치는 데이터 테이블 Feature에서 확정한다"고 공통으로 미뤄온 값들이다. Notion 작업 페이지의 System "데이터 테이블"과 그 아래 3개 Feature("플레이어,고양이 스탯 관련 데이터 테이블", "음식 장애물 생성 관련 데이터 테이블", "점수 집계 관련 데이터 테이블")가 바로 이 System에 대응한다(1-6절). 이번 세션에는 Notion에 접근하는 도구가 연결되어 있지 않아 Notion 원문은 직접 확인하지 못했고, 사용자가 프롬프트로 전달한 요약과 로컬 코드베이스·과거 계획서 조사로만 계획을 작성했다.
- 이 계획의 성격: 최초 계획서에서 사용자가 명시적으로 미확정이라고 밝혔던 항목들이 이후 두 차례에 걸쳐 모두 결정되었다 — (A) 어떤 데이터부터 옮길지는 `SpeedEffectData`를 제외한 5개, 단순한 것부터 파이프라인을 검증하는 순서로 결정됨(0-1, 0-2절). (B) 가져오는 방식은 "에디터 시점 + 공개 TSV export(인증 불필요)"로 결정됨(0-3절, 두 축 모두 확정). `AnimationCurve` 필드 제외(0-6절)도 결정됨. 남은 것은 시트 레이아웃 승인(0-5)과 Notion 확인(0-8) 두 가지뿐이며, 이 둘은 계속 추측으로 대신 결정하지 않는다(7절). 이제 신규 파일 4개(`DataTableRow`/`DataTableRowParser`/`DataTableFetcher`/`DataTableAssetWriter`) 전부를 구체적인 코드로 설계했다(4절) — 이 계획은 더 이상 "결정과 무관한 부분만" 다루지 않고, 실제로 구현 가능한 수준까지 내려왔다.
- 범위 밖으로 명시하는 것
  - 실제 Google 스프레드시트에 컬럼·값을 입력하는 작업. 이 계획은 시트 구조(스키마)를 "제안"만 하며, 시트에 실제로 그 구조를 만드는 것은 사용자 또는 별도 단계의 몫이다.
  - 6개 스텁 SO의 실제 밸런싱 수치 확정. 그 수치들은 이미 각자의 Feature 계획에서 "개발 테스트용 임시값"이라고 명시돼 있고(1-1절), 이 계획은 "무엇으로 채울지"가 아니라 "어떻게 채우는 파이프라인을 만들지"를 다룬다.
  - Google 계정 쪽 설정 작업(시트 공유 범위를 실제로 "링크가 있는 모든 사용자"로 바꾸는 것 포함). 계정 관리는 사용자 소유 영역이라 코드 계획에 포함하지 않는다. 다만 이번 결정(0-3)으로 이 설정이 필수가 되었다는 사실 자체는 0-7절·4-6절에 기록한다.
  - `SpeedEffectData`. 사용자 주석(0-1/0-2절)으로 이번 데이터 테이블 대상에서 제외됐다. 이 SO에 남아있는 "정식 수치는 데이터 테이블 Feature에서 확정한다" 문구를 앞으로 어떻게 처리할지(다른 Feature로 옮기는지, 값을 그대로 Inspector 수동값으로 확정하는지 등)는 이번 결정에 포함되지 않은 별개의 사안이라 이 계획에서 다루지 않는다.
- 인접 Feature와의 경계
  - 6개 스텁 SO를 참조하는 기존 6개 Feature(배고픔 속도 시스템, 고양이 AI, 풀잎 비행, 오브젝트 랜덤 생성, 속도 연출, 점수 랭킹 시스템)의 소비 코드(`HungerController`, `CatController`, `Player`, `ObjectSpawner`, `SpeedEffectController`, `ScoreController` 등)는 이번 계획에서 전혀 수정하지 않는 것을 원칙으로 세운다(0-4절 근거). 이 데이터 테이블 Feature는 SO 필드에 "값이 채워지는 경로"만 새로 추가하고, 그 값을 읽는 소비자 쪽 API(프로퍼티 이름, 타입)는 그대로 유지한다.

## 0. 결정 사항과 아직 확정되지 않은 사항

### 0-1. 이 Feature가 다루는 대상 — 결정됨(5개, `SpeedEffectData` 제외)

사용자가 최초 프롬프트에 나열한 후보는 `CatStatData`/`PlayerStatData`/`LeafFlightData`/`ObjectSpawnData`/`SpeedEffectData` 5개였다. 코드베이스 전체를 조사한 결과 동일한 "정식 수치는 데이터 테이블 Feature에서 확정한다" 문구를 가진 클래스가 **6개** 있었다 — `ScoreData`(`Assets/02_Scripts/Score/ScoreData.cs`)가 최초 목록에 없었다(26_0923에 추가되어 사용자가 목록 작성 시점에 놓쳤을 가능성).

**결정** (사용자 주석 근거): `ScoreData`는 포함하고, `SpeedEffectData`는 제외한다. 최종 대상은 **5개** — `ScoreData`, `LeafFlightData`, `CatStatData`, `PlayerStatData`, `ObjectSpawnData`.

6개 모두 `Assets/05_Data/*.asset`에 실제 에셋 인스턴스가 있다(`PlayerStatData.asset`, `CatStatData.asset`, `LeafFlightData.asset`, `ObjectSpawnData.asset`, `SpeedEffectData.asset`, `ScoreData.asset`). `SpeedEffectData.asset`은 이 Feature가 값을 채우지 않는다.

### 0-2. 어떤 데이터부터 옮길지 — 결정됨

**결정** (사용자 주석 근거): 0-1에서 확정된 5개 중, 가장 단순한 것부터 시작해 파이프라인을 검증한 뒤 나머지로 확장하는 순서로 진행한다.

| SO 클래스 | 필드 수 | 타입 구성 | 복잡도 비고 |
|---|---|---|---|
| `ScoreData` | 3 | float x3 | 가장 단순 |
| `LeafFlightData` | 3 | float x3 | 가장 단순 |
| `SpeedEffectData` | 6 | float x6 | (0-1 결정으로 이번 범위에서 제외) |
| `CatStatData` | 7 | float x7 | 단순 |
| `PlayerStatData` | 5 | float x4 + AnimationCurve x1 | 커브 1개는 0-6 결정으로 이번 범위에서 제외(나머지 4개 float는 포함) |
| `ObjectSpawnData` | 21 | float x15 + int x5 + bool x1 | 필드 수 최다, 타입이 가장 다양함 |

필드 수 기준 가장 단순한 것은 `ScoreData`와 `LeafFlightData`(각 float 3개)로 동률이다 — 사용자 주석에 이 둘 중 어느 쪽을 먼저 검증용으로 삼을지는 명시되지 않았고, 둘 다 구조가 동일(float 3개, 시트 3행)하므로 구현 단계에서 어느 쪽으로 시작해도 결과에 차이가 없다. 이후 확장 순서는 필드 수 기준 `CatStatData`(7) → `PlayerStatData`(5, 커브 제외 시 실질 4) → `ObjectSpawnData`(21)가 자연스럽다.

대상 5개의 필드 총합은 39개(3+3+7+5+21)이며, 이 중 `PlayerStatData`의 `AnimationCurve` 1개를 뺀 **38개가 이번 데이터 테이블의 실제 대상 필드**다(0-6절).

### 0-3. 스프레드시트 → Unity 가져오기 방식 — 결정됨(에디터 시점 + 공개 TSV export, 인증 불필요)

사용자가 최초에 예시로 든 두 후보는 "에디터 전용 수동 임포트"와 "빌드에 API 키를 넣는 런타임 방식"이다. 조사해보면 이 둘은 사실 **서로 독립된 두 축**의 조합 중 일부라는 점이 드러난다.

- 축 1 — **언제 값이 적용되는가**: 에디터에서 미리 가져와 `.asset`에 구워 넣는가, 아니면 런타임에 그때그때 가져오는가. **→ 결정됨: 에디터 시점.**
- 축 2 — **인증이 필요한가**: Google Sheets API 키/서비스 계정이 필요한가, 아니면 시트를 공개 공유해 인증 없이 export URL로 읽을 수 있는가. **→ 결정됨(사용자 지시 근거): 인증 불필요 — 공개 TSV export.**

두 축을 표로 교차하면 다음과 같다(결정된 한 칸만 남기고 나머지는 제외).

| | 인증 필요(Sheets API 키/서비스 계정) | 인증 불필요(공개 TSV export) |
|---|---|---|
| **에디터 시점에 가져와 `.asset`에 굽기** | ~~(제외됨)~~ | **결정됨 — 채택** |
| ~~런타임(빌드 실행 중)에 그때그때 가져오기~~ | ~~(제외됨)~~ | ~~(제외됨)~~ |

CSV가 아니라 TSV를 쓰는 이유: 4-1절 스키마의 `Description` 컬럼은 기획자가 쓰는 한글 자유 문장이라 쉼표가 들어갈 수 있다. CSV였다면 그 경우 따옴표 이스케이프 처리가 필요해지는데, 탭 문자는 일반 문장에 거의 나오지 않아 TSV가 이 스키마에 더 안전하다.

이 결정에 따라 2-2절 "가져오기(`DataTableFetcher`)"를 4-3절에 구체적으로 설계했다. 시트를 "링크가 있는 모든 사용자 - 보기 가능"으로 공유해야 한다는 전제 조건이 생기며, 이는 0-7절·4-6절(다음 단계)에서 다룬다.

### 0-4. 기존 SO 클래스/필드 계약을 유지할지 — 임시 해석(확인 필요)

6개 SO 클래스 전부가 "정식 수치는 데이터 테이블 Feature에서 확정한다"는 문구를 반복해왔다(1-1절). 이 문구는 "SO 클래스 자체가 이 Feature의 결과물로 대체된다"가 아니라 "이 SO가 들고 있는 값이 시트에서 온 값으로 채워진다"로 해석하는 것이 문맥상 가장 자연스럽다 — 소비 코드 6곳이 이미 이 SO 타입들을 `[SerializeField]`로 참조하도록 각자의 계획에서 확정돼 있고, 그 계약을 바꾸면 6개 Feature 전부의 재작업이 필요해지기 때문이다. 이 계획은 이 해석을 임시로 채택해 "SO 필드 구조(클래스·프로퍼티)는 그대로 두고 `.asset`의 값만 시트에서 채운다"는 설계로 진행한다(4절). 다르게 의도했다면(예: SO를 걷어내고 다른 런타임 조회 구조로 바꾸는 것을 원한다면) 알려주면 고친다.

### 0-5. 시트 레이아웃(스키마) — 제안(변경 가능, 4-1절에서 구체화)

사용자가 명시적으로 미확정이라고 밝힌 항목과 달리, 시트를 "테이블(클래스)당 탭 하나 + 필드를 컬럼으로" 배치할지 "탭 하나에 모든 테이블의 필드를 행으로 나열"할지는 사용자가 아직 언급하지 않은 구현 세부 사항이다. 이 계획은 후자(탭 1개, 행 = 필드 1개)를 제안하고 근거를 남긴다(4-1절) — 다만 이것도 확정이 아니라 "변경 가능한 제안"이다.

### 0-6. `AnimationCurve` 필드(`PlayerStatData._hungerToSpeedCurve`) 처리 — 결정됨(제외)

대상 5개(0-1절) 39개 필드 중 유일하게 스칼라 값이 아닌 필드다. 스프레드시트 셀 하나로 곡선(여러 키프레임)을 표현하는 방법이 마땅치 않았다.

**결정** (사용자 주석 근거): 이 필드는 이번 데이터 테이블 구현 대상에서 제외하고, 계속 Inspector에서 직접 수동 관리한다. 나머지 38개 필드는 전부 float/int/bool 스칼라라 문제가 없다.

### 0-7. Google 시트 공유 설정 — 필수 조건(결정됨), 실제 적용 여부는 실행 단계에서 확인 필요

0-3절에서 "공개 TSV export(인증 불필요)"로 결정되어, 시트가 최소 "링크가 있는 모든 사용자 - 보기 가능"으로 공유돼 있어야 한다는 것 자체는 더 이상 선택이 아니라 필수 조건이다. 다만 "MouseAndCheeseTable" 시트의 현재 실제 공유 설정은 이번 조사로 확인하지 못했다(이 계획을 작성하는 도구에는 시트 권한을 조회하는 기능이 없다). 구현 착수 전 실제로 이 설정이 돼 있는지 확인하고, 안 돼 있다면 사용자가 직접 바꿔야 한다(계정 설정 변경은 이 계획의 범위 밖). 4-6절 "다음 단계"의 실행 항목으로 옮겨 관리한다.

### 0-8. Notion "데이터 테이블" System의 Task 내용 — 미확인

프로젝트 메모리(2026-09-17 기록)에 "데이터 테이블 System의 3개 Feature에 구체적인 밸런싱 값 정의 Task를 채웠다"는 기록이 있지만, 이번 세션에는 Notion에 접근하는 도구가 연결돼 있지 않아 그 Task 본문을 직접 확인하지 못했다. 다만 26_0923 계획서(점수 랭킹 시스템)는 "점수 집계 관련 데이터 테이블" Feature의 Task 1("생존시간/사과/치즈 점수 가중치 값 정의")이 그 시점엔 "본문 없음, 제목만 존재"였다고 기록했다. **확인 필요**: 구현 착수 전에 Notion 작업 페이지의 "데이터 테이블" System 3개 Feature를 다시 열어, 이번 결정(0-3)에 참고할 내용이 이미 채워져 있는지 먼저 확인하는 편이 안전하다.

### 1-2. 네이밍 컨벤션 확인 — private `_camelCase` 필드 ↔ public `PascalCase` 프로퍼티, 예외 없는 1:1 규칙

6개 클래스의 45개 필드를 전부 대조한 결과, 예외 없이 다음 규칙이 성립한다: `[SerializeField] private <타입> _fieldName;`에 대해 `public <타입> FieldName => _fieldName;`가 있고, `FieldName`은 `_fieldName`의 첫 글자만 대문자로 바꾼 것과 정확히 같다(예: `_maxHunger` ↔ `MaxHunger`, `_elevatedWeightMultiplier` ↔ `ElevatedWeightMultiplier`). 이 규칙은 4-2절 파서가 시트의 "필드명" 컬럼(사람이 읽기 쉬운 `PascalCase`)을 실제 직렬화 필드 이름으로 기계적으로 되돌리는 데 근거로 쓰인다.

## 4. 단계별 구현 내용

### 4-1. 제안 시트 스키마 (변경 가능, 0-5절)

탭 1개(예: 이름 `DataTable`)에, 필드 1개 = 행 1개인 "긴 형식(long format)"을 제안한다. 대상은 0-1/0-2에서 확정된 5개 클래스, 38개 스칼라 필드다(`PlayerStatData`의 커브 필드는 0-6에 따라 제외).

| Table | Field | Type | Value | Description |
|---|---|---|---|---|
| PlayerStatData | MaxHunger | float | 100 | 배고픔 게이지 최대치 |
| PlayerStatData | HungerDecayPerSecond | float | 2 | 초당 배고픔 감소량 |
| ObjectSpawnData | RestrictHeight | bool | FALSE | 높이 제한 구간 사용 여부 |
| ... | ... | ... | ... | ... |

- `Table` 컬럼 값은 SO 클래스 이름과 정확히 같다(예: `PlayerStatData`).
- `Field` 컬럼 값은 `public` 프로퍼티 이름(`PascalCase`)과 정확히 같다(예: `MaxHunger`) — 1-2절의 1:1 규칙으로 직렬화 필드 이름을 기계적으로 되돌릴 수 있다.
- `Type`은 `float`/`int`/`bool` 중 하나다(`AnimationCurve`는 0-6절에 따라 이번 스키마에서 제외).
- `SpeedEffectData`는 0-1절 결정에 따라 이 표에 행을 만들지 않는다.
- 클래스별 탭을 따로 두는 대안(탭 = 클래스, 컬럼 = 필드, 행 1개만 존재)도 검토했다 — 이 방식은 "표처럼 보인다"는 장점이 있지만, 인스턴스가 클래스당 1개뿐이라 실제로는 헤더 행 + 값 행 1개짜리 표가 되어 장점이 크지 않고, 새 필드가 추가될 때마다 여러 탭에 컬럼을 늘려야 한다. 긴 형식은 새 필드가 그냥 새 행이 되고, `Description` 컬럼으로 필드별 설명을 붙이기 쉬워 이번 계획은 긴 형식을 제안한다.

### 4-2. 공통 골격 — `DataTableRow` / `DataTableRowParser` (확정)

```csharp
using System.Collections.Generic;

/// <summary>
/// 시트에서 파싱한 데이터 테이블 한 행을 담는 클래스
/// </summary>
public class DataTableRow
{
    /// <summary>
    /// 값을 적용할 대상 ScriptableObject 클래스 이름
    /// </summary>

    /// <summary>
    /// 값을 적용할 대상 프로퍼티 이름
    /// </summary>
    public string FieldName { get; set; }

    /// <summary>
    /// 값의 타입을 나타내는 문자열("float", "int", "bool")
    /// </summary>
    public string ValueType { get; set; }

    /// <summary>
    /// 문자열 그대로의 값
    /// </summary>
    public string Value { get; set; }

    /// <summary>
    /// 기획자가 남기는 설명
    /// </summary>
    public string Description { get; set; }
}
```

```csharp
using System.Collections.Generic;

/// <summary>
/// 원시 셀 격자를 DataTableRow 목록으로 변환한다
/// </summary>
public class DataTableRowParser
{
    private const int ColumnTable = 0;
    private const int ColumnField = 1;
    private const int ColumnType = 2;
    private const int ColumnValue = 3;
    private const int ColumnDescription = 4;

    /// <summary>
    /// 첫 행을 헤더로 보고 건너뛴 뒤 나머지 행을 DataTableRow로 변환한다
    /// </summary>
    public List<DataTableRow> Parse(IReadOnlyList<string[]> rawGrid)
    {
        List<DataTableRow> rows = new List<DataTableRow>();
        for (int i = 1; i < rawGrid.Count; i++)
        {
            string[] cells = rawGrid[i];
            if (cells.Length <= ColumnValue)
            {
                continue;
            }

            DataTableRow row = new DataTableRow();
            row.TableName = cells[ColumnTable];
            row.FieldName = cells[ColumnField];
            row.ValueType = cells[ColumnType];
            row.Value = cells[ColumnValue];
            row.Description = cells.Length > ColumnDescription ? cells[ColumnDescription] : string.Empty;
            rows.Add(row);
        }

        return rows;
    }
}
```

`Parse`의 입력 `IReadOnlyList<string[]>`(행마다 셀 문자열 배열)는 4-3절 `DataTableFetcher`가 만드는 격자와 정확히 같은 모양이라 그대로 이어 붙일 수 있다. 첫 행(헤더)은 건너뛴다.

### 4-3. 가져오기 — 공개 TSV export로 결정되어 확정된 구현 (`DataTableFetcher`)

```csharp
using System;
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.Networking;

/// <summary>
/// 공개 공유된 "MouseAndCheeseTable" 시트를 TSV로 내려받아 원시 셀 격자로 변환한다(에디터 전용)
/// </summary>
public static class DataTableFetcher
{
    private const string SpreadsheetId = "1g5WEcxEHic73LiLZFZlbchHXNLCDCjxaHyoAk7KLXFs";
    private const int SheetGid = 0;

    /// <summary>
    /// DataTable 탭을 TSV로 내려받아 셀 격자로 반환한다. 실패하면 빈 격자를 반환한다
    /// </summary>
    public static IReadOnlyList<string[]> FetchGrid()
    {
        string url = $"https://docs.google.com/spreadsheets/d/{SpreadsheetId}/export?format=tsv&gid={SheetGid}";

        using UnityWebRequest request = UnityWebRequest.Get(url);
        UnityWebRequestAsyncOperation operation = request.SendWebRequest();

        // 에디터 메뉴 명령이라 코루틴 없이 완료를 기다린다
        while (operation.isDone == false)
        {
        }

        if (request.result != UnityWebRequest.Result.Success)
        {
            Debug.LogError($"시트 다운로드 실패: {request.error}\n시트가 '링크가 있는 모든 사용자 - 보기 가능'으로 공유돼 있는지 확인하세요.");
            return Array.Empty<string[]>();
        }

        return ParseGrid(request.downloadHandler.text);
    }

    /// <summary>
    /// TSV 텍스트를 줄바꿈과 탭 기준으로 잘라 셀 격자로 만든다
    /// </summary>
    private static IReadOnlyList<string[]> ParseGrid(string tsvText)
    {
        string normalized = tsvText.Replace("\r\n", "\n").Replace("\r", "\n");
        string[] lines = normalized.Split('\n');

        List<string[]> grid = new List<string[]>();
        for (int i = 0; i < lines.Length; i++)
        {
            if (string.IsNullOrEmpty(lines[i]))
            {
                continue;
            }

            grid.Add(lines[i].Split('\t'));
        }

        return grid;
    }
}
```

- `SpreadsheetId`는 "MouseAndCheeseTable"의 실제 파일 ID([[project_mouse_and_cheese_data_table_sheet]] 메모리 근거)다. `SheetGid = 0`은 시트의 기본 첫 번째 탭을 그대로 "DataTable"로 이름만 바꿔 쓴다고 가정한 값이다 — 새 탭을 별도로 추가해 "DataTable"을 만든다면(기본 탭이 아니라면) 그 탭의 실제 gid로 바꿔야 한다.
- `while (operation.isDone == false) { }`로 동기 대기하는 것은 에디터 메뉴 명령 실행 중 잠깐 UI가 멎는 대신 코루틴 없이 간단하게 구현하는 방식이다 — 사용자가 공유한 참고 구현(`GoogleSheetDownloader`)이 `HttpClient.GetAsync(...).Result`로 동일한 트레이드오프를 택한 것과 같은 이유다.
- 실패 시(`request.result != Success`) 빈 격자를 반환하고 `Debug.LogError`로 원인을 알린다 — 다운로드 실패가 조용히 넘어가 값이 하나도 안 바뀐 채 "성공"처럼 보이는 사고를 막기 위함이다. 이는 시트에 없는 필드를 건너뛰는 정상 분기(4-4절)와 마찬가지로, 실제 실패를 사용자에게 알리는 정상적인 에러 로그이지 디버깅용 임시 로그가 아니다.
- 이 파일은 `UnityWebRequest`만 쓰고 `UnityEditor`는 참조하지 않아 엄밀히는 `Editor` 폴더 밖에 둬도 컴파일된다. 다만 이 Feature 전체가 에디터 전용으로 설계됐고(0-3 축 1) 실제로 에디터 메뉴에서만 호출되므로, 일관성을 위해 `DataTableAssetWriter`와 같은 `Editor` 폴더에 둔다.

### 4-4. 값 적용 — 에디터 시점으로 결정되어 확정된 구현 (`DataTableAssetWriter`)

```csharp
using System.Collections.Generic;
using System.Globalization;
using UnityEditor;
using UnityEngine;

/// <summary>
/// DataTableRow 목록을 대상 ScriptableObject 필드에 적용한다(에디터 전용)
/// </summary>
public static class DataTableAssetWriter
{
    /// <summary>
    /// tableName과 일치하는 행을 target의 SerializedProperty에 쓰고 저장한다
    /// </summary>
    public static void Apply(ScriptableObject target, List<DataTableRow> rows, string tableName)
    {
        SerializedObject serializedObject = new SerializedObject(target);
        for (int i = 0; i < rows.Count; i++)
        {
            DataTableRow row = rows[i];
            if (row.TableName != tableName)
            {
                continue;
            }

            string fieldName = ToBackingFieldName(row.FieldName);
            SerializedProperty property = serializedObject.FindProperty(fieldName);
            if (property == null)
            {
                continue;
            }

            ApplyValue(property, row);
        }

        serializedObject.ApplyModifiedProperties();
        EditorUtility.SetDirty(target);
    }

    /// <summary>
    /// 프로퍼티 이름(PascalCase)을 직렬화 필드 이름(_camelCase)으로 바꾼다
    /// </summary>
    private static string ToBackingFieldName(string propertyName)
    {
        return "_" + char.ToLowerInvariant(propertyName[0]) + propertyName.Substring(1);
    }

    /// <summary>
    /// 프로퍼티 타입에 맞춰 문자열 값을 파싱해 대입한다
    /// </summary>
    private static void ApplyValue(SerializedProperty property, DataTableRow row)
    {
        switch (property.propertyType)
        {
            case SerializedPropertyType.Float:
                property.floatValue = float.Parse(row.Value, CultureInfo.InvariantCulture);
                break;
            case SerializedPropertyType.Integer:
                property.intValue = int.Parse(row.Value, CultureInfo.InvariantCulture);
                break;
            case SerializedPropertyType.Boolean:
                property.boolValue = bool.Parse(row.Value);
                break;
        }
    }
}
```

- `float.Parse`/`int.Parse`에 `CultureInfo.InvariantCulture`를 명시한 이유: 시스템 로케일에 따라 소수점 구분자가 쉼표로 해석되는 환경이 있어, 지역화 문자로 파싱이 실패하거나 엉뚱한 값이 들어가는 사고를 막기 위함이다.
- `ApplyValue`의 `switch`는 `float`/`int`/`bool` 세 타입만 처리한다. `AnimationCurve`(0-6절로 제외된 필드)나 그 외 타입이 들어오면 아무 것도 하지 않고 조용히 넘어간다 — 이 침묵은 "디버깅 로그를 위한 null 체크를 하지 않는다"는 컨벤션과는 다른 문제로, `switch`가 다루지 않는 타입을 조용히 건너뛰는 정상 분기다.
- 이 파일은 `UnityEditor`를 참조하므로 반드시 이름이 `Editor`인 폴더 아래에 있어야 한다(1-3절). 이 프로젝트에 `UnityEditor`를 참조하는 사용자 코드가 아직 없으므로, 이 파일이 만들어지면 **이 프로젝트 최초의 에디터 전용 스크립트**가 된다.
- 0-3 두 축이 모두 결정되어, `DataTableFetcher.FetchGrid()` → `DataTableRowParser.Parse()` → 이 `Apply()`를 그대로 이어 붙일 수 있다. SO 에셋 5개 각각에 대해 `Apply`를 호출하는 진입점(에디터 메뉴 아이템)은 4-6절 "다음 단계"에서 실제 구현 시 추가한다.

### 4-5. `AnimationCurve` 필드 처리 (0-6절, 결정됨)

`PlayerStatData._hungerToSpeedCurve`만 예외적으로 이번 스키마·`ApplyValue`에서 제외한다. 곡선은 여러 개의 (시간, 값) 키프레임으로 이뤄져 있어 "값 1개짜리 셀"과 형태가 다르기 때문이다. 이 필드는 계속 Inspector에서 직접 편집하는 것으로 남겨둔다(사용자 주석으로 확정).

## 6. 주의 사항 및 설계 결정 근거

1. **소비 코드 6곳을 전혀 수정하지 않는 것을 원칙으로 세운 이유(0-4절)**: 6개 SO 클래스는 이미 각자의 Feature 계획서에서 "정식 수치는 데이터 테이블 Feature가 채운다"는 전제로 설계·리뷰·구현이 끝난 상태다. 이 전제를 뒤집어 SO 자체를 다른 구조로 바꾸면 6개 Feature 전부를 다시 열어야 하므로, 이번 계획은 가장 보수적인 해석(값만 채운다)을 기본으로 삼았다.
2. **`DataTableFetcher`를 이제 구체적으로 작성한 이유**: 이전 버전 계획에서는 인증 축(0-3 축 2)이 미정이라 가져오기 코드를 쓰면 추측으로 결정을 대신하는 셈이었다. 이번에 축 2가 "공개 TSV export"로 확정되어, 그 결정을 그대로 구현한 것뿐 새로운 추측을 더하지 않았다(0-3절).
3. **`DataTableAssetWriter`를 `Editor` 폴더 아래에 두어야 하는 이유**: 이 프로젝트는 `.asmdef`로 에디터/런타임 어셈블리를 나누지 않고 Unity의 "폴더 이름이 `Editor`" 규칙에 의존한다(1-3절). `UnityEditor.SerializedObject`를 참조하는 코드를 `Editor` 폴더 밖에 두면 플레이어 빌드가 컴파일에 실패한다. `DataTableFetcher`는 이 제약이 엄밀히는 없지만(4-3절), 일관성을 위해 같은 폴더에 뒀다.
4. **`float.Parse`에 `CultureInfo.InvariantCulture`를 명시한 이유**: 실행 환경의 로케일에 따라 소수점 구분자가 달라질 수 있어, 이를 고정하지 않으면 같은 시트 값이 환경에 따라 다르게 파싱되는 재현하기 어려운 버그로 이어질 수 있다.
5. **`AnimationCurve`를 스키마에서 제외한 이유(0-6절)**: 이번 스키마(4-1절)는 "필드 1개 = 값 1개"를 전제로 하는데 곡선은 값이 여러 개(키프레임)라 같은 셀 모델로 표현할 수 없다. 억지로 한 셀에 인코딩하는 방법도 있지만, 그 인코딩 형식 자체가 사용자가 정하지 않은 새로운 결정이라 이번 계획에 포함하지 않았다.
6. **`.asset`이 Force Text로 직렬화된다는 사실(1-5절)이 이 설계를 더 안전하게 만드는 이유**: 데이터 테이블 값을 반복해서 다시 가져와 `.asset`을 덮어써도 git diff가 필드별로 사람이 읽을 수 있게 남아, 실수로 잘못된 값이 들어갔을 때 커밋 리뷰로 바로 드러난다.
7. **이번에 채택한 조합의 실전 근거**: "에디터 시점 + 인증 불필요(공개 TSV)" 조합은 기획자가 스프레드시트에서 밸런스를 관리하면서 빌드에는 시크릿이 들어가지 않게 하려는 목적에 자주 쓰인다 — API 키 관리 자체가 필요 없고 빌드에도 아무 자격 증명이 들어가지 않기 때문이다. 실제로 사용자가 대화 중 공유한 참고 구현(`GoogleSheetDownloader`)도 인증 헤더 없이 export URL만 호출하는 동일한 방식이었다. 다만 업계 전반, 특히 팀 규모가 커진 프로덕션에서는 시트를 비공개로 유지하고 CI 자동화가 가능한 서비스 계정 방식이 더 일반적이라는 점도 참고로 남긴다 — 이번 프로젝트는 1인 개발 초기 단계라는 맥락에서 공개 TSV를 채택했다.
8. **Notion 원문을 이번 세션에서 직접 확인하지 못했다는 한계(0-8절)**: 이 계획은 사용자가 프롬프트로 전달한 요약과 프로젝트 메모리·과거 계획서만으로 작성됐다. 구현 착수 전 Notion "데이터 테이블" System의 Task 본문을 다시 확인하는 절차를 건너뛰지 않는 것을 권장한다.
9. **코딩 컨벤션 준수**: 이번 계획의 코드 스니펫은 모두 접근 제어자를 명시했고, `var`를 쓰지 않았으며, 람다식을 쓰지 않았고, `!` 대신 조건식(`== false`, 비교 연산자)을 사용했으며, 클래스·메서드·public 멤버에 한국어 `<summary>`를 달았고, 디버깅 로그 목적의 null 체크는 없다(`property == null`, 다운로드 실패 로그 모두 정상적인 분기이며 디버깅 목적이 아니다).
