## 0. 확정되지 않아 이번 계획에서 임의로 결정하지 않은 사항 (구현 단계 전 확인 필요)

Notion Task 3개가 제목만 있고 본문이 비어 있어, 아래 항목은 추측으로 채우지 않고 이번 계획의 한계로 명시한다.

1. **정확한 연출 수치**: 기본/목표 FOV 값, 블러 최대 강도, 각 효과가 목표값에 도달하는 속도(스무딩 시간) 등 구체적인 숫자는 Notion에 전혀 없다. `SpeedEffectData`(4-1절)에 개발 테스트용 임시 플레이스홀더만 채워뒀으며, 정식 수치는 플레이테스트 또는 "데이터 테이블" Feature에서 확정해야 한다.
2. **"카메라 관성"의 정확한 의미**: 두 가지 해석이 가능하다.
   - (A) FOV 값이 임계값을 넘나들 때 즉시 스냅되지 않고 서서히(SmoothDamp) 전환되는 것 자체를 "관성"으로 본다 — 이번 계획이 **채택한 최소 해석**(4-2절).
   - (B) 카메라 위치/회전이 플레이어를 살짝 지연 추종하거나(포지션 랙), 고속 이동 시 흔들리거나 기울어지는(스웨이/틸트) 별도의 이펙트.
   - (B)는 `CameraController.FollowPlayer()`(피벗을 매 프레임 즉시 플레이어 위치로 스냅)와 `HandleCollision()`(카메라-피벗 거리를 이미 자체 SmoothDamp로 제어)이라는 기존 로직과 같은 Transform을 두고 경쟁하게 되어, 구현 방식에 따라 두 개의 스무딩이 서로 간섭(feedback)할 위험이 있다. 또한 랙의 크기/축(위치? 회전?)이 전혀 명세되지 않았다. 이번 계획은 (B)를 포함하지 않았으며, 필요하면 별도로 사양을 확정한 뒤 `CameraController.cs` 수정 여부를 재논의해야 한다(CLAUDE.md 파일 수정 규칙 — 수정 전 사용자 확인 필수).
3. **"게이지 75% 이상"(Task 1, `HungerRatio` 기준 문구)과 "`CurrentMoveSpeed`가 트리거 조건"(사용자 확인 요구사항)을 함께 만족시키는 절충안**: `PlayerStatData.EvaluateMoveSpeed(0.75f)`로 환산한 속도를 임계값으로 삼아 `CurrentMoveSpeed`와 비교하는 방식을 채택했다(4-2절 `IsSpeedBoosted()`). 이 절충 해석이 실제 의도와 맞는지 확인이 필요하다. 이 변환은 `EvaluateMoveSpeed`의 매핑 곡선이 **단조증가**라는 전제에 의존한다 — 현재 기본 곡선(`AnimationCurve.Linear(0,0,1,1)`)은 단조증가이므로 지금은 문제가 없지만, 추후 밸런싱 곡선이 U자형 등으로 바뀌면 "게이지 75%"와 "속도 임계값"이 더 이상 같은 지점을 가리키지 않게 될 수 있다.
4. **발동/해제 경계에서의 진동(hunting) 방지 여부**: 단일 임계값 하나만 쓰고 `SmoothDamp`로 값 변화를 완충하는 정도로만 처리했다. 임계값 근처에서 속도가 미세하게 오르내리면 목표값(0 또는 최대치)이 계속 바뀌면서 `SmoothDamp`가 매번 새 목표를 쫓는 상태가 될 수 있다. on/off에 서로 다른 임계값을 두는 히스테리시스 설계는 명세가 없어 포함하지 않았다.
5. **라디얼 블러 셰이더의 세부 알고리즘 수치**: 샘플 수(8), 블러 방향 계산 방식 등은 모두 동작 확인 전 임시값이며, 실제 화면에서 시각적으로 검증되지 않았다.
6. **렌더러 적용 범위**: "툰 셰이더" Feature 선례(2절)를 따라 `PC_Renderer.asset`에만 적용하고 `Mobile_Renderer.asset`은 범위에서 제외하는 것으로 제안했다. 별도 확인이 필요하다.
7. **기존 `MotionBlur`(URP 내장 Volume 컴포넌트) 재사용 여부**: 씬의 Global Volume이 참조하는 `SampleSceneProfile.asset`에 `MotionBlur` 컴포넌트가 이미 존재하지만 `active: 0`으로 비활성 상태임을 확인했다(1-3절). 이번 계획은 이를 재사용하지 않고 별도의 라디얼 블러 셰이더를 새로 만드는 쪽을 택했다(6-6절 근거 — URP `MotionBlur`는 카메라/오브젝트의 실제 화면상 움직임을 기반으로 하는 이펙트라 "정지 상태에서도 속도감을 표현하는 방사형 블러"라는 요청과 결이 다르다고 판단). 이 판단이 맞는지 확인이 필요하다.

## 1. 코드베이스 조사 결과

### 1-1. 트리거 소스 확인 (`HungerController`, `PlayerStatData`)
- `Assets/02_Scripts/Hunger/HungerController.cs`: `public float HungerRatio => Mathf.Clamp01(_currentHunger / _playerStatData.MaxHunger);`, `public float CurrentMoveSpeed => _playerStatData.EvaluateMoveSpeed(HungerRatio);` 둘 다 캐싱 없이 매 호출 즉시 계산되는 프로퍼티다(주석에 "`CameraController.ForwardDirection`과 동일 패턴, 한 프레임 지연 회피"라고 명시). 이번 계획도 이 값을 매 프레임 폴링만 하고 캐싱하지 않는 동일 패턴을 따른다.
- `Assets/02_Scripts/Hunger/PlayerStatData.cs`: `public float EvaluateMoveSpeed(float hungerRatio)`가 이미 `public`으로 노출되어 있어, 이번 계획도 이 메서드를 그대로 재사용해 "게이지 75%"를 속도 단위로 환산할 수 있다(수정 불필요).

### 1-2. 카메라 계층 구조 확인 (`Assets/04_Prefabs/Player.prefab`)
- `Player`(루트, `CharacterController`/`InputManager`/`Player`/`HungerController`/`PlayerPathRecorder`) 아래에 `CameraPivot` 자식이 있고, `CameraPivot`에 `CameraController` 컴포넌트가 부착되어 있다(`_inputManager`/`_cameraTransform`/`player`/`_pivotHeight` 등 필드 확인).
- `CameraPivot`의 자식으로 `Main Camera`가 있으며, `Camera` 컴포넌트(`field of view: 60`)와 `UniversalAdditionalCameraData`(`m_VolumeLayerMask: Bits 1`(Default 레이어), `m_VolumeTrigger: {fileID: 0}`)를 갖는다. `CameraController._cameraTransform`이 바로 이 `Main Camera`의 Transform을 가리킨다.
- 즉 FOV를 제어하려면 이 `Main Camera` GameObject의 `Camera` 컴포넌트에 접근해야 하며, `CameraController`와 동일하게 `CameraPivot`에 형제 컴포넌트로 신규 스크립트를 붙이고 `Camera`를 `[SerializeField]`로 직접 연결하는 방식이 기존 관례(모든 참조는 인스펙터 직결, DI 프레임워크 없음)와 일치한다.

### 1-3. URP 화면 효과 인프라 확인
- `Packages/manifest.json`에 `com.unity.render-pipelines.universal: 17.3.0` 확인. URP Volume 프레임워크가 실제로 사용 중이다 — `SampleScene.unity`에 `Global Volume` GameObject가 존재(1178행)하고, 그 프로파일(`Assets/Settings/SampleSceneProfile.asset`)에는 `Bloom`/`Vignette`/`Tonemapping`/`MotionBlur` 4개 컴포넌트가 있다. 이 중 `MotionBlur`는 `active: 0`(비활성)으로 확인됨.
- URP Volume 오버라이드 중 "라디얼 블러"에 해당하는 내장 컴포넌트는 없다(Bloom/Vignette/ColorAdjustments/DepthOfField/LensDistortion/MotionBlur/PaniniProjection/ShadowsMidtonesHighlights/SplitToning/FilmGrain/ChromaticAberration/WhiteBalance/ColorCurves/ColorLookup/ChannelMixer/ScreenSpaceLensFlare가 전부 — `Assets/Settings/DefaultVolumeProfile.asset` 전수 확인). 따라서 라디얼 블러는 **커스텀 셰이더로 직접 구현해야 한다**(0-7절 판단 근거).
- `Assets/Settings/PC_Renderer.asset`(Universal Renderer Data)에 Renderer Feature가 이미 2개 등록되어 있음을 확인: `ScreenSpaceAmbientOcclusion`(SSAO)과 **`FullScreenPassRendererFeature`**(`injectionPoint: 600` = `AfterRenderingPostProcessing`, `fetchColorBuffer: 1`, `requirements: 3` = Depth+Normal, `passMaterial: ToonOutline_Mat.mat`). 이 `FullScreenPassRendererFeature`는 "툰 셰이더" Feature가 외곽선(`Assets/03_Shaders/ToonOutlineFullScreen.shader`)에 쓰고 있는 것으로, 코드 작성 없이 화면 전체에 커스텀 셰이더를 적용하는 URP 내장 메커니즘임을 재확인했다(`Assets/Ignore/Task/Plan/26_0912_툰쉐이더_plan.md` 5-1절과 동일한 인프라).
- `Assets/03_Shaders/ToonOutlineFullScreen.shader`를 직접 읽어, URP 코어의 `Blit.hlsl`(`Packages/com.unity.render-pipelines.core/Runtime/Utilities/Blit.hlsl`)이 제공하는 `Vert(Attributes)`/`Varyings{positionCS, texcoord}`/`_BlitTexture`를 그대로 재사용하는 표준 구조를 확인했다. `Blit.hlsl`을 직접 읽어 `sampler_LinearClamp`/`sampler_PointClamp`가 `GlobalSamplers.hlsl`을 통해 이미 선언되어 있음도 확인했다(4-3절 셰이더 코드의 근거).
- 결론: 라디얼 블러도 이 **"두 번째 `FullScreenPassRendererFeature` + 전용 머티리얼"** 패턴을 그대로 재사용하면, 별도의 `ScriptableRendererFeature` C# 코드를 새로 작성할 필요가 없다(기존 툰 외곽선과 동일 인프라 재사용, 6-2절 근거).

### 1-4. `Player.cs`/`CameraController.cs`의 기존 이벤트·프로퍼티 패턴
- `Player.OnMoveStateChanged`(Run/Fly), `HungerController.OnHungerChanged` 등 이벤트가 있지만, 이번 계획은 이벤트 구독이 아니라 **매 프레임 폴링** 방식을 택했다(6-3절 근거 — `GapDistanceUI`가 `CatController.Gap`을 매 프레임 폴링하는 선례와 동일하게, 연속적으로 부드럽게 변해야 하는 시각 효과(FOV/블러 강도)는 이벤트 기반보다 폴링 기반이 자연스럽다).
- 모든 컴포넌트 간 참조는 `[SerializeField]` 인스펙터 직결 방식이며, `GetComponent`/`GetComponentInChildren`은 같은 프리팹 내부의 `Awake()`에서만 제한적으로 쓰인다. DI 프레임워크·Singleton·ServiceLocator 없음(기존 관례, 이번 계획도 동일하게 따름).

## 4. 단계별 구현 내용

### 4-1. `SpeedEffectData.cs` (신규, 임시 스텁)

```csharp
using UnityEngine;

/// <summary>
/// 속도 연출(카메라 FOV·관성, 화면 라디얼 블러)의 밸런싱 수치를 담는 임시 스텁 ScriptableObject.
/// 정식 수치는 "데이터 테이블" Feature에서 확정한다(0-1절 참고)
/// </summary>
[CreateAssetMenu(fileName = "SpeedEffectData", menuName = "MouseAndCheese/Speed Effect Data")]
public class SpeedEffectData : ScriptableObject
{
    [Header("발동 조건")]
    [SerializeField] private float _hungerRatioThreshold = 0.75f;

    [Header("카메라 FOV")]
    [SerializeField] private float _baseFov = 60f;
    [SerializeField] private float _boostedFov = 75f;
    [SerializeField] private float _fovSmoothTime = 0.5f;

    [Header("화면 라디얼 블러")]
    [SerializeField] private float _maxBlurIntensity = 0.3f;
    [SerializeField] private float _blurSmoothTime = 0.5f;

    /// <summary>
    /// 연출이 발동하는 배고픔 비율 임계값(0~1). CurrentMoveSpeed와 비교하기 위해
    /// PlayerStatData.EvaluateMoveSpeed로 속도 단위로 환산해서 쓴다(0-3절, 4-2절 근거)
    /// </summary>
    public float HungerRatioThreshold => _hungerRatioThreshold;

    /// <summary>
    /// 평상시(비발동) 카메라 시야각
    /// </summary>
    public float BaseFov => _baseFov;

    /// <summary>
    /// 연출 발동 시 목표 카메라 시야각
    /// </summary>
    public float BoostedFov => _boostedFov;

    /// <summary>
    /// FOV가 목표값에 도달하는 대략적인 시간(SmoothDamp의 smoothTime, 관성감 조절용)
    /// </summary>
    public float FovSmoothTime => _fovSmoothTime;

    /// <summary>
    /// 연출 발동 시 라디얼 블러의 최대 강도(0~1)
    /// </summary>
    public float MaxBlurIntensity => _maxBlurIntensity;

    /// <summary>
    /// 블러 강도가 목표값에 도달하는 대략적인 시간(SmoothDamp의 smoothTime)
    /// </summary>
    public float BlurSmoothTime => _blurSmoothTime;
}
```

### 4-2. `SpeedEffectController.cs` (신규)

```csharp
using UnityEngine;

/// <summary>
/// HungerController.CurrentMoveSpeed를 폴링해 임계 속도 이상이면 카메라 FOV를 넓히고
/// 화면 라디얼 블러 강도를 높이는 연출을 담당하는 클래스. CameraPivot 오브젝트에 부착한다
/// </summary>
public class SpeedEffectController : MonoBehaviour
{
    private static readonly int BlurIntensityId = Shader.PropertyToID("_BlurIntensity");

    [SerializeField] private HungerController _hungerController;
    [SerializeField] private PlayerStatData _playerStatData;
    [SerializeField] private SpeedEffectData _speedEffectData;
    [SerializeField] private Camera _camera;
    [SerializeField] private Material _radialBlurMaterial;

    private float _fovVelocity;
    private float _blurVelocity;
    private float _currentBlurIntensity;

    /// <summary>
    /// 카메라 FOV를 평상시 값으로 초기화한다
    /// </summary>
    private void Start()
    {
        _camera.fieldOfView = _speedEffectData.BaseFov;
    }

    /// <summary>
    /// 매 프레임 발동 조건을 확인하고, 목표 FOV와 블러 강도로 서서히 근접시킨다.
    /// CameraController.LateUpdate()(피벗 추종, 벽 충돌 회피)와 동일한 타이밍에 맞춰
    /// 그 프레임의 최종 이동 상태를 반영하도록 LateUpdate에서 처리한다
    /// </summary>
    private void LateUpdate()
    {
        bool isBoosted = IsSpeedBoosted();

        float targetFov = isBoosted ? _speedEffectData.BoostedFov : _speedEffectData.BaseFov;
        _camera.fieldOfView = Mathf.SmoothDamp(_camera.fieldOfView, targetFov, ref _fovVelocity, _speedEffectData.FovSmoothTime);

        float targetBlur = isBoosted ? _speedEffectData.MaxBlurIntensity : 0f;
        _currentBlurIntensity = Mathf.SmoothDamp(_currentBlurIntensity, targetBlur, ref _blurVelocity, _speedEffectData.BlurSmoothTime);
        _radialBlurMaterial.SetFloat(BlurIntensityId, _currentBlurIntensity);
    }

    /// <summary>
    /// 현재 이동 속도가 임계 배고픔 비율(HungerRatioThreshold)에 해당하는 속도 이상인지 판정한다.
    /// 비교 자체는 요구사항에 따라 HungerRatio가 아니라 CurrentMoveSpeed로 수행하며,
    /// PlayerStatData.EvaluateMoveSpeed로 임계 비율을 속도 단위로 환산해 비교한다(0-3절 근거)
    /// </summary>
    private bool IsSpeedBoosted()
    {
        float thresholdSpeed = _playerStatData.EvaluateMoveSpeed(_speedEffectData.HungerRatioThreshold);
        return _hungerController.CurrentMoveSpeed >= thresholdSpeed;
    }
}
```

### 4-3. `SpeedRadialBlur.shader` (신규)

```hlsl
Shader "Custom/SpeedRadialBlur"
{
    Properties
    {
        _BlurIntensity("Blur Intensity", Range(0, 1)) = 0
    }

    SubShader
    {
        Tags { "RenderType" = "Opaque" "RenderPipeline" = "UniversalPipeline" }

        Pass
        {
            Name "SpeedRadialBlur"
            ZTest Always
            ZWrite Off
            Cull Off

            HLSLPROGRAM
            #pragma vertex Vert
            #pragma fragment SpeedRadialBlurFragment

            // ToonOutlineFullScreen.shader와 동일한 include 순서(Core.hlsl 먼저, XR 텍스처 매크로 정의 후 Blit.hlsl)
            #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"
            // Vert()/Varyings/_BlitTexture/sampler_LinearClamp는 URP 코어의 Blit.hlsl(및 그 안의 GlobalSamplers.hlsl)이 제공
            #include "Packages/com.unity.render-pipelines.core/Runtime/Utilities/Blit.hlsl"

            // 컴파일 타임 상수 — 런타임 프로퍼티로 노출하지 않아 셰이더 복잡도를 낮춘다(0-5절 근거)
            #define SAMPLE_COUNT 8

            CBUFFER_START(UnityPerMaterial)
                half _BlurIntensity;
            CBUFFER_END

            half4 SpeedRadialBlurFragment(Varyings input) : SV_Target
            {
                float2 uv = input.texcoord;
                float2 center = float2(0.5, 0.5);
                // 화면 중심→현재 픽셀 방향으로, 강도(_BlurIntensity)만큼 샘플 지점을 중심 쪽으로 당겨
                // 방사형(radial) 블러를 만든다. 강도 0이면 모든 샘플이 원본 uv와 같아져 블러가 사라진다
                float2 direction = (uv - center) * _BlurIntensity;

                half4 accumulatedColor = half4(0, 0, 0, 0);

                // SAMPLE_COUNT가 컴파일 타임 상수라 언롤 가능한 고정 루프
                for (int i = 0; i < SAMPLE_COUNT; i++)
                {
                    float t = (float)i / (SAMPLE_COUNT - 1);
                    float2 sampleUV = uv - direction * t;
                    accumulatedColor += SAMPLE_TEXTURE2D_X_LOD(_BlitTexture, sampler_LinearClamp, sampleUV, 0);
                }

                return accumulatedColor / SAMPLE_COUNT;
            }
            ENDHLSL
        }
    }
}
```

### 4-4. `SpeedRadialBlur_Mat.mat` (신규) + `PC_Renderer.asset` 수정 (Unity Editor 작업)

셰이더 파일 저장 시 Unity가 GUID를 새로 발급하므로, 머티리얼과 Renderer Feature 연결은 계획 문서에 YAML을 직접 적을 수 없고 에디터에서 수행해야 한다(`ToonOutline_Mat.mat` 선례와 동일한 이유).

1. `Assets/03_Shaders` 우클릭 → Create → Material → 이름을 `SpeedRadialBlur_Mat`으로 지정 → Shader를 `Custom/SpeedRadialBlur`로 변경.
2. `Assets/Settings/PC_Renderer.asset` 선택 → Inspector → Add Renderer Feature → **Full Screen Pass Renderer Feature**(두 번째 항목, 기존 툰 외곽선용 항목은 그대로 둔다) 추가.
   - `requirements`: **None** (라디얼 블러는 `_BlitTexture`만 필요하고 Depth/Normal은 필요 없다 — 기존 툰 외곽선 항목의 `requirements: 3`(Depth+Normal)과 다름, 1-3절 근거).
   - `passMaterial`: 1번에서 만든 `SpeedRadialBlur_Mat.mat` 연결.
   - `injectionPoint`: `AfterRenderingPostProcessing`(기존 툰 외곽선 항목과 동일 — 최종 화면 색상 위에 마지막으로 합성되어야 하므로).
   - Renderer Feature 목록에서 툰 외곽선 항목보다 **아래(나중)**에 위치하도록 추가한다(같은 injectionPoint를 공유하는 여러 Renderer Feature는 목록 순서대로 실행되므로, 라디얼 블러가 외곽선 이후에 적용되도록 순서를 보장한다).

### 4-5. Unity Editor 수동 작업 (코드 외 작업)

1. `SpeedEffectData` 에셋 1개를 임시로 생성(우클릭 → Create → MouseAndCheese → Speed Effect Data).

## 6. 주의 사항 및 설계 결정 근거

1. **`CameraController.cs`를 전혀 수정하지 않음**: 카메라 관련 신규 로직(FOV)을 기존 파일에 섞지 않고 같은 `CameraPivot` 오브젝트에 형제 컴포넌트(`SpeedEffectController`)로 분리했다. `CameraController`는 회전/추종/벽 충돌이라는 이미 복잡한 책임을 지고 있고, "카메라 관성"의 정확한 메커니즘이 미확정(0-2절)이라 섣불리 그 파일의 `FollowPlayer()`/`HandleCollision()`에 손대면 기존 SmoothDamp 로직과 충돌할 위험이 있다고 판단했다. `CameraController.cs`는 사용자가 직접 관리해 온 파일이므로 어차피 수정하려면 별도 승인이 필요하다(CLAUDE.md 파일 수정 규칙).
2. **라디얼 블러를 URP Volume 오버라이드가 아니라 `FullScreenPassRendererFeature` + 전용 머티리얼로 구현**: URP 17.3.0에 내장된 Volume 오버라이드 중 라디얼 블러에 해당하는 것이 없음을 직접 확인했다(1-3절). 반면 "툰 셰이더" Feature가 이미 같은 목적(화면 전체에 커스텀 셰이더 적용)으로 `FullScreenPassRendererFeature`를 성공적으로 쓰고 있어, 같은 인프라를 재사용하면 새 `ScriptableRendererFeature` C# 코드를 작성할 필요가 없다. Volume 프레임워크의 파라미터 블렌딩(여러 Volume이 겹칠 때의 가중 평균)이 필요하다는 요구사항도 없으므로, 단일 전역 머티리얼에 스크립트로 직접 `SetFloat`하는 더 단순한 방식을 택했다.
3. **이벤트 구독이 아니라 매 프레임 폴링 방식 채택**: `HungerController.OnHungerChanged` 이벤트를 구독할 수도 있었지만, FOV/블러 강도는 이산적인 "값이 바뀐 순간"이 아니라 매 프레임 연속적으로 `SmoothDamp`되어야 하는 값이라 이벤트 기반보다 폴링 기반이 자연스럽다. `GapDistanceUI`가 `CatController.Gap`을 매 프레임 읽는 기존 선례와 같은 패턴이다.
4. **"게이지 75% 이상"과 "`CurrentMoveSpeed` 트리거"를 `PlayerStatData.EvaluateMoveSpeed` 환산으로 절충**: 0-3절에서 설명한 대로, 사용자가 명시한 트리거 소스(`CurrentMoveSpeed`)를 문자 그대로 지키면서도 Notion Task 1의 "게이지 75%" 문구를 반영하기 위해, 임계값을 배고픔 비율(0.75)로 정의해두고 비교 시점에 `PlayerStatData.EvaluateMoveSpeed`로 속도 단위로 환산했다. `HungerRatio`를 직접 비교하지 않은 이유는 사용자 확인 요구사항이 명시적으로 "CurrentMoveSpeed"를 트리거 조건으로 지목했기 때문이다.
5. **`SpeedEffectData`를 `PlayerStatData`/`LeafFlightData`/`CatStatData`와 동일한 ScriptableObject 임시 스텁 패턴으로 설계**: 프로젝트 전역에서 수치를 가진 새 Feature마다 이 패턴이 반복적으로 채택되어 온 것을 확인했다(1-1절, `CatStatData.cs` 참고). `CameraController`처럼 `[SerializeField]`를 직접 들고 있는 방식도 고려했으나, 이번 수치들은 "카메라 자체의 조작감"이 아니라 "연출 밸런싱 수치"에 가까워 데이터 테이블 Feature가 나중에 흡수하기 쉬운 ScriptableObject 쪽이 기존 관례와 더 잘 맞는다고 판단했다.
6. **`SAMPLE_COUNT`를 셰이더 프로퍼티가 아니라 `#define` 상수로 고정**: 런타임에 샘플 수를 바꿀 요구사항이 없고, 상수로 두면 컴파일 타임에 루프가 언롤되어 성능상 이점이 있다(0-5절 — 세부 수치 자체는 여전히 임시값).
7. **`Player.cs`/`HungerController.cs`/`PlayerStatData.cs`/`CameraController.cs`를 전혀 수정하지 않음**: 네 파일 모두 기존 공개 API(`CurrentMoveSpeed`, `EvaluateMoveSpeed`, `ForwardDirection` 패턴 등)만으로 이번 요구사항을 충족할 수 있어 수정이 필요 없었다. `PC_Renderer.asset`(Renderer Feature 추가)과 `Player.prefab`(컴포넌트 부착)만 실제 변경 대상이며, 둘 다 4-4/4-5절에 명시된 대로 실제 작업 전 별도 사용자 확인이 필요하다.
8. **코딩 컨벤션 준수**: 모든 필드/메서드에 접근 제어자 명시, `var` 미사용, `!` 대신 조건식 사용(단일 부정 케이스 없음), 클래스·public 멤버에 한국어 `<summary>` XML 주석 작성, 람다식 미사용, 디버깅 목적의 null 체크 없음(`_hungerController` 등 필수 참조 미연결 시 `NullReferenceException`이 그대로 발생하는 fail-fast 방식 — `HungerController`/`LeafFlightTrigger`의 기존 결정과 동일).
